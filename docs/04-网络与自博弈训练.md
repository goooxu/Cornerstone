# 网络与自博弈训练

## CornerNet

自研结构，围绕两件事设计。

### 一、低精度 GEMM 是主体

主干由 **PolyBlock** 堆叠：

```
x = x + DepthwiseConv5x5(RMSNorm(x))        空间混合，FLOPs 占比 <2%
x = x + Attention(RMSNorm(x))               每 4 个 block 一次，196 个格 token 全局注意力
x = x + SwiGLU(RMSNorm(x))                  通道混合，D -> 4D -> D，FLOPs 主体
```

深度可分离卷积提供局部归纳偏置但几乎不耗算力；真正吃算力的是 SwiGLU 里那两个大 GEMM
和注意力的四个投影 —— 这些全部经由 `make_linear()` 创建，把这一个函数换掉
就切到 FP8 / FP4，不动主干代码（`ModelConfig.precision`）。

输出头：

- **策略头** `D -> 91`，每个格给出 91 个朝向的 logit，转置展平成 `ori*196 + cell`，
  正好对上引擎的动作编码
- **价值头** WDL 三分类 softmax。本项目和局是真实结果（随机对局下 4.5%），
  tanh 标量没法区分「这是和棋局面」和「胜负各半的混沌局面」
- **辅助头** 终局占格数差回归。信号比稀疏的三分类密集得多，早期收敛主要靠它

`D=256, blocks=16` 时 **14.2M 参数**。

### 二、零拷贝的双视图

张量全程保持 `(B, 196, D)` 连续布局。关键性质：**一个连续的 `(B,196,D)` 张量
在物理上就是 channels_last 的 `(B,D,14,14)`**，所以

```python
xc = x.view(B, 14, 14, D).permute(0, 3, 1, 2)     # 纯视图，data_ptr 不变
y  = conv(xc)                                      # cuDNN channels_last 快路径
back = y.permute(0, 2, 3, 1).reshape(B, 196, D)    # 纯视图
```

两边都不产生拷贝。不注意这一点的话，每个 block 要来回两次 200 MB 级别的转置 ——
16 个 block 就是 6 GB 的无谓搬运。有单测（`test_token_view_is_really_zero_copy`）
拿 `data_ptr()` 守着这条性质。

### 策略头零初始化

`policy.weight` 和 `bias` 都初始化为 0，于是训练第一步的先验就是**合法着法上的均匀分布**。
不这么做的话，MCTS 一开始就被一个随机的强先验带偏，自博弈数据的质量会差很多。

## Gumbel AlphaZero

用 Gumbel-AZ 而不是原版 AlphaZero，是被 Blokus 的形状逼出来的：动作空间 17836，
单步合法着法常有几百个（开局就有 414 个）。原版靠 PUCT + Dirichlet 噪声探索，
在这种宽度下要很大的模拟数才能让根节点的访问分布有统计意义。
Gumbel-AZ 在根节点用 Gumbel top-k 采样出 m 个候选、再用 sequential halving 分配预算，
**低模拟数下的策略改进有理论保证**。

实现要点：

- 根节点：`g_a + log π(a)` 取 top-m 作为候选；每轮给每个候选 `n/(R·|S|)` 次访问，
  轮末按 `g_a + log π(a) + σ(q_a)` 砍掉一半
- 内部节点：`argmax_a [ improved_π(a) − N(a)/(1+ΣN) ]`，
  `improved_π = softmax(log π + σ(completed_q))`，未访问动作的 q 用 `v_mix` 补全
- **回传符号不能按深度奇偶定**。Blokus 有停手规则，同一方可能连走两手，
  所以每个节点存自己的行棋方，回传时按实际行棋方定符号

### 批量方式：多局并行，单局单叶子

同时开很多局，**每局在任意时刻只有一个待评估的叶子**。批量大小来自局数，
不是单局内的并行叶子数。这样：

- 不需要 virtual loss（单局内不会有并发的搜索路径）
- 不需要多线程回调 Python（Python 驱动循环，C++ 只做树的工作）

驱动循环：

```python
while True:
    n = engine.prepare(planes, scalars)   # C++，已释放 GIL
    if n: engine.feed(*model(planes[:n], scalars[:n]))
    else: games += engine.advance()
```

## 训练目标的存法：稀疏 top-K + 尾部质量

策略目标**不做归一化**，存 top-32 的原始概率外加一个 `rest_prob`。

这不是省事，是必须的。实测训练早期 `rest_prob ≈ 0.90` —— 先验接近均匀、
合法着法几百个时，top-32 只装了约 10% 的概率质量。
若把 top-32 归一化当目标，等于在教网络集中到一组**本质上任意**的着法上
（未访问动作之间只按先验排序，而先验此时是均匀的）。

训练时把 `rest_prob` 均摊到其余合法着法上：

```
loss = -( Σ_top p_a·log q_a  +  rest_prob · mean_{a∈legal\top} log q_a )
```

一个隐蔽的坑：补位槽（`n_top` 之后的槽）概率是 0，但**动作编号必须仍指向合法着法**。
否则 gather 会取到 `-inf` 的 log 概率，再乘 0 就是 NaN。代码里用第 0 个
（一定合法）的动作填充补位槽，并且在损失里用 `where` 而不是乘法屏蔽。

## Replay buffer：只存着法序列

一局约 27 手，每手 32 个 `(int32 动作, fp32 概率)` ≈ 260 B，加着法本身约 **7 KB/局**。
稠密策略目标是每手 17836 个 float = 71 KB/**手** —— 差三个数量级。
工作目录只剩百来 GB，这是唯一可行的存法。

局面特征在取批时由 C++ `build_batch` 从着法序列**重建**：每局只回放一次、
一次性吐出该局被抽中的全部 ply（所以要求 ply 递增，Python 侧先按 `(局, 手)` 排序）。
CPU 有 144 核，用算力换存储是划算的。

对称增广也在 `build_batch` 里做完：几何变换直接作用在特征平面和合法掩码上，
稀疏策略目标的动作编号重映射留给 Python（一次 numpy 花式索引）。

**正确性由单测守着**：`test_build_batch_matches_plain_replay` 逐字节比对
`build_batch` 的输出与「用 Board 老老实实回放一遍」的结果。这条不测的话，
训练数据错了也很难从 loss 曲线上看出来。

## 评测记录不能进 replay buffer

评测模式下网络方用搜索、对手用规则基线，对局记录里**只有网络方走的手**
（随机开局和对手的着法都没记）。从空棋盘回放这样的序列会得到非法着法序列。

记录里带一个 `selfplay` 标记，`ReplayBuffer.add_records` 直接拒绝非自博弈记录。
不加这道拦截的话，要等到 `build_batch` 里 `Board::play` 抛异常才会暴露，那时已经很难查。

## 学习率日程：WSD

`TrainConfig.lr_schedule` 有两种：

| | 形状 |
|---|---|
| `cosine` | warmup 线性上 → 余弦退到 `lr * min_lr_ratio`（历史默认，`v2-*` 用的是它） |
| `wsd` | warmup → **stable 段恒等于 `lr`** → 末段线性退到 `lr * min_lr_ratio` |

选 WSD 是为了一件事：**「训多久」不必在一开始指定。**
余弦的形状被总步数整体决定，改总预算等于换一条曲线，之前的进度不能接着用；
WSD 的 stable 段与总预算无关，想收工时才花最后约 10% 退火，
而且 stable 段上的**任何一步**都可以当分叉点，退出不同的终点。

### `lr_horizon_steps` 是这套东西成立的前提

三个字段各管一件事，**不能合并**：

```
lr_horizon_steps   曲线自己的横轴终点（0 = 跟随 total_steps，向后兼容）
lr_decay_steps     末段退火步数（0 = horizon 的 10%）
total_steps        **这一次**跑到哪停 —— 只管停，不管形状
```

退火窗口若锚在 `total_steps` 上（`decay_start = total_steps − decay`），
那么「训完 11.1 万觉得还能再练，把 `total_steps` 改成 25 万」的那一刻，
已经退到 2e-4 的学习率会**跳回 2e-3**。那不是加训，是先做了一次 warm restart
再加训 —— 而两者在日志上长得一模一样。
`test_wsd_decay_window_does_not_move_when_total_steps_changes` 守这条。

余弦分支也改用 `horizon` 了，`horizon=0` 时逐位等于改动前（另有一条测试逐位比对），
所以 `v2-*` 的复现不受影响。

### 交付点 A

```
--lr-schedule wsd --total-steps 111000 --lr-horizon-steps 111000 --lr-decay-steps 11000
```

→ warmup 500 → **stable 恒 2e-3 到 100,000** → 线性退到 2e-4 @ **111,000**（退火占 9.9%）。

选 10 万做 stable 的依据是实测：**92% 的棋力在 8 万步就到手**，
之后每万步的增量（+2 ~ +12 Elo）已落在测量误差 ±9.6 之内。
10 万步已经越过那个点，而总步数比原来的 15 万每组省约 26%。
退火用**线性**：文献上 1−sqrt 略好，但这个项目没测过，不引入第二个变量。

**风险**：stable 把 2e-3 顶了 10 万步，平均学习率远高于余弦。
实测 `grad_norm` 约 0.36 而 `grad_clip=1.0`，预计稳定，但头 20 轮要盯梯度范数。

### 峰值在哪：分叉退火，以及三个精度并不在同一处见顶

「练到多少步棋力最强」这个问题，**不能拿一条跑的中间档去回答**。WSD 的中间档
是**还在 stable 段、学习率顶着 2e-3** 的权重，它和「按这个预算训练、正常退火」
出来的模型是两回事。要问「如果当初只给 8 万步会怎样」，就得真的按 8 万步的
日程退火一次。

做法叫**分叉退火**：留着 stable 段的里程碑档和**同一步的 replay 快照**，
从第 X 步分叉出去，只跑退火段。这就是 `maybe_snapshot_milestone()` 和
`replay_snapshot/stepNNNNNNNN.npz` 存在的理由 —— 只留权重不留 replay 的话，
分叉出来的跑要拿一个**别的时刻**的经验池接着训，测的就不是同一件事了。

三个精度各测 14 个退火点（早期 67k/78k/89k/100k/111k + 晚期 122k…211k），
每点一场 400 局的全对全 arena，联合 Bradley-Terry 拟合：

| | 67k | 78k | 89k | 100k | **111k** | 122k | 133k | 144k | 155k | 167k | 178k | 189k | 200k | 211k |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| BF16 | −49 | −46 | −28 | −15 | **0** | −5 | +5 | −15 | +7 | +8 | −22 | −38 | −51 | −36 |
| FP8 | −53 | −30 | −21 | −20 | **0** | +14 | | **+29** | | +10 | | −5 | | +5 |
| FP4 | −16 | +8 | +7 | +11 | **0** | +1 | +5 | +6 | −18 | −29 | −24 | −31 | −28 | −30 |

每格相对**同精度自己的 111k**，单格 ±11~14。结论按误差读，不要按名次读：

| 精度 | 平台 | 实用峰值 | 练过头的代价 |
|---|---|---|---|
| BF16 | 111k–167k（15 Elo 内） | **111k** | 178k 起真下滑，200k −51 |
| FP8 | 122k–167k | **144k**（比自己 111k **+29 ± 14**） | 189k 起回落，但不崩 |
| FP4 | 78k–144k（21 Elo 内） | **~100k** | 155k 起下滑，稳定 −25~−31 |

**三条曲线的形状不一样，这是这轮最有用的一条。** 看 67k→111k 那段涨幅：
BF16 +49、FP8 +53、**FP4 只有 +15**。FP4 在 78k 就已经到自己的天花板，
之后 6 万步一分不涨；而 FP8 是唯一一个练过 111k 还在涨的。
**所以「练多少步」这件事不能跨精度照抄。**

#### 早期和晚期两条曲线怎么接到一把尺子上

早期点分叉自重训的 `v4-<p>-e100`，晚期点分叉自原始跑 —— **两条不同的轨迹**
（同种子也不重合：100k 处 loss 差 0.10）。直接把两张 Elo 表拼起来是错的。

办法是让两条轨迹的 111k 模型**在同一场 arena 里直接对打**。实测 BF16
`fork-a111` 与 `main-a111` 差 **2.4 Elo**，FP8 差 7.4，FP4 差 2.4 ——
都在一个标准误以内，于是两张表可以平移对齐。这个校正项必须**测**，
不能假设它是 0。

一个具体的坑：`net_arena` 用文件名里的 `step(\d+)` 给参赛者命名，
两条轨迹的 111k 档**同名同步数**，会被当成同一个参赛者悄悄合并。
`runs/_arena/` 下的软链因此故意**不带 `step`**（`fork-a111.pt` /
`main-a111.pt`），让命名退回文件名。

### 分叉点要自己留

跨进退火段的那一步会额外落一份**永久**的 `ckpt/stable.pt` 与
`replay_snapshot/stable.npz`。默认机制留不住它，两个理由各自独立成立：

* replay 快照只有一份，每次 `save_snapshot()` 覆盖同一个文件
* 里程碑保留的是「每个 `milestone_every_steps` 桶里的**第一份**」，
  而 stable 终点（100,000）落在桶 10 里，桶 10 早被 100,0xx 之前的某一份占了

这份旁档**不更新 `latest`** —— 它是分叉点不是进度。让 `latest` 指过去的话，
下次恢复出来的进程会把「已落过 stable」这个进程内标志重置，
于是又往 `stable.pt` 上写一份已经在退火段里的权重，分叉点悄悄漂走。
（磁盘上已经有 `stable.pt` 时也直接认它、不覆盖，理由同上。）

### 训练结束之后：收割

训练档（`ckpt/`）与发布包（`model/`）分工相反，**保留规则也相反**：

| | 留什么 | 谁读 |
|---|---|---|
| `ckpt/` | **只留为继续训练而存在的两份**：`stable.pt`（WSD 分叉点）与 `latest` 指向的终点档 | 只有续训 |
| `model/` | **一份都不少**，每个里程碑都有 | 评测、web、诊断 |

`model/` 一份不能少，是因为棋力阶梯要靠中间档画曲线，删了就没法复现；
`ckpt/` 只留两份，是因为一份 162.5 MiB 而它唯一的用途是接着训。
做法与理由见 [`docs/06`](06-低精度训练.md) 的「训练产物 → 推理部署」。

### 加训之前必须先修的一个坑

跑满之后再启动一次，训练循环会立刻 `break`，一步没训就掉进收尾的
`save_checkpoint()` —— 而 AdamW 的 `state` 是**懒创建**的、此时还空着。
结果是一份**没有动量**的档覆盖掉同名的里程碑，replay 快照也被重写。
磁盘上已经发生过：

```
runs/v2-bf16/ckpt/step00140227.pt   170 MB   有 exp_avg
runs/v2-bf16/ckpt/step00150227.pt    56 MB   无 exp_avg   <- latest 指向它
```

守护脚本每 3 分钟查一次，配置一改就会走这条路径；**WSD 的「续跑下一段」
更是每次都要经过它**。现在改成一步没训就直接 `return`，不落盘。

## 端到端自检

`tools/train.py --smoke` 用一套小配置（0.8M 参数、128 并行局、32 次模拟）
跑通「自博弈 → replay → 训练 → 落盘」的完整环路，几分钟出结果。
用途是改完代码验证管线没断，不是拿来出棋力结论的。

判断标准很简单：价值损失要从 `ln3 ≈ 1.099`（三分类的均匀分布）明显往下走，
策略熵要单调下降。

> 原先还有一条「对 `greedy-area` 的得分率要能越过 0.5」。训练期的周期性评测
> 已经移除（规则基线量不了这个网络，见 [08](08-已知问题与后续.md)），
> 这条判据随之失效 —— 要看棋力得事后跑 `tools/net_arena.py`。

## 吞吐

这个模型很瘦（D=256），一开始自博弈是**核函数启动受限**的：单次前向约 10 ms
且与批大小几乎无关。C++ 侧从来不是瓶颈（128 线程 1030 万次着法生成/s）。

优化过程与最终数字见 [07-性能调优.md](07-性能调优.md)。

## 加宽到头了：这套数据预算下约 30M 参数就是天花板

D=256（14.2M）一路加宽到 384（31.7M）、512（56.3M），两种精度各测了一遍。
**学习率按 1/宽度 同步调过**（不调的话测的是学习率没调好，不是宽度，见下）。

同 144k 步预算、同一把 FP4 尺子（`_ruler/v4-fp4-100k.pt`）为锚：

| | BF16 | FP4 |
|---|---:|---:|
| 256 → 384 | **−24.2 ± 10.2** | **+21.9 ± 11.0** |
| 384 → 512 | 未测 | **−2.1 ± 11.6**（直接对局 0.491 / 1200 局） |

`runs/arena_v5-lr.json`、`runs/arena_v5-lr-fp4.json`、`runs/arena_fp4-width.json`。

三件事：

**1. 384 → 512 是零。** 参数量翻 1.8 倍，−2.1 ± 11.6，直接对局 0.491 ——
与五五开无法区分。加宽这根轴到此为止，再堆宽度不会有收益。

**2. 加宽在 BF16 是负的、在 FP4 是正的。** 看着矛盾，其实一致：
低精度的量化噪声相当于一笔**容量税**，加宽是在把被税掉的有效容量赎回来；
BF16 没有这笔税，在 256 上就已经被数据量卡住了，多给参数只是更难训。
两条线最后收敛到同一个天花板 —— 也就是说瓶颈不在参数量，**在每步喂进去的
自博弈局数**。

**3. 学习率不是宽度中性的。** 同样是 384，`lr=2e-3`（照搬 256 的值）
比按 1/宽度 调成 `1.3e-3` 差 **46.4 Elo**（BF16）和 **179.8 Elo**（FP4）。
FP4 上差出近 180 分 —— 不调学习率去比宽度，量到的基本是学习率的锅。
`scripts/ab_experiment.sh` 的 `lr_for` 按实验名写死了这条规律，别绕过它。

> **复现校验**：`d384-lr13` 在两轮独立 arena 里分别是 +21.8 ± 11.2 和
> +21.9 ± 11.0，对 `d256` 的直接得分率两次都是 0.475。整套测量是稳的 ——
> 上面那些个位数的差值确实就在噪声里，不是流程漂移。

## 另一根轴：Qwen3-0.6B 形状的 28 层双向骨干

加宽到头之后换的是**骨干形状**。`ModelConfig.arch` 选骨干，`"poly"`（默认，
即上面那套深度卷积 + 每 4 层一次注意力）或 `"qwen"`。层的实现在
`cornerstone/qwen_block.py`，输入嵌入与三个头仍在 `CornerNet` 里 ——
所以量化、导出、权重分发、编译那一整套原样复用，没为新骨干改第二遍。

**只借形状，不载任何预训练权重，全部随机初始化。** 实验名前缀 `qwen-` 很容易
被读成「从 Qwen3-0.6B 微调来的」，那是本项目最防的那类误读：不报错、跑得通、
结论全错。代码里没有任何一处会去 HuggingFace 拉权重。

不叫 `v7-` 也是这个理由：`v4/v5/v6` 是同一根 poly 骨干在改宽度和学习率，
编号连着走是有含义的，换骨干还用 `v7` 会被读成同一条线的下一代。

| | Qwen3-0.6B | 本项目 `arch="qwen"` |
|---|---|---|
| 层数 | 28 | 28 |
| hidden | 1024 | 1024 |
| 注意力 | 16 Q / 8 KV（GQA），head_dim 128 | 同（注意 16×128=2048≠hidden，是 Qwen3 的设计） |
| MLP | SwiGLU，intermediate 3072 | 同 |
| 归一化 | RMSNorm pre-norm + QK-Norm | 同 |
| 方向 | **因果** | **双向** |
| 位置编码 | **1D RoPE** | **2D RoPE** |
| 输入 | 文本 token | 结构化棋盘与棋子嵌入 |
| 输出 | LM 头 | 合法动作策略头 + 局面价值头 |

参数量 **445.1M**（骨干约 440M + 嵌入与三个头约 4.4M）。

### 两处有意的偏离

**双向注意力。** 棋盘上 240 个 token 同时可见，没有「未来」可言；因果 mask
会让第 k 个格子看不到它右边和下边的棋盘，是纯粹的信息损失。

**2D RoPE。** Qwen3 的 1D RoPE 编码的是 token 在序列里的次序，而 14×14 棋盘
没有次序 —— 按行优先展开时 (0,13) 与 (1,0) 的下标只差 1，棋盘上却隔着整整
一行。这里把 `head_dim` 劈成两半，前一半按 row 旋转、后一半按 col 旋转。
**两半必须各自配对旋转**：整条 head_dim 一起转的话，行的后半会和列的前半配成
一对，两个坐标轴就串了 —— 串了之后网络照样能训，只是位置编码是乱的，
loss 上完全看不出来。棋子/标量 token 不在棋盘上，角度取 0，RoPE 退化成恒等，
它们的位置信息由各自的可学习嵌入提供。

### 序列布局（240 token）

```
[ cell_0   .. cell_195 ]  196 个格 token，逐格 nn.Linear(PLANES, d) 投影
[ own_0    .. own_20   ]   21 个己方棋子 token（在手/已用 各一个可学习向量）
[ opp_0    .. opp_20   ]   21 个对方棋子 token
[ score_own, score_opp ]    2 个标量 token
```

四类各加一个 type embedding。`trunk()` 只把**前 196 个 token** 交给三个头，
池化也只在这 196 个上做 —— 头部形状与 poly 骨干逐字一致，
`mask_logits` 与动作编号 `ori*196+cell` 一个字都不用改。

### 三个静默坑（都有测试盯着，见 `tests/test_qwen_arch.py`）

1. **RoPE 表必须 `persistent=False`。** `pool.py` 的 `_layout()` 只遍历
   `named_parameters()`，靠「模型没有 buffer」这个前提把权重打平分发；
   而 `model.py` 的 `load_weights()` 对 state_dict 里的未知键直接抛错。
   持久 buffer 两头都会出事。表是 cfg 的确定性函数，每个 worker 各建一份即可。
2. **MLP 必须叫 `mlp`。** `train.py` 的 `_compile_hot_modules` 写死了
   `blk.mlp.compile(...)`，改名它会静默不编译，表现只是「训练慢了一截」，
   没有任何报错。
3. **`shape_for` 必须在 `${COMMON[@]}` 之后展开。** COMMON 里有
   `--blocks 16`，排在后面才能被 `--blocks 28` 覆盖。第一次起跑就栽在这儿：
   建出来的是 256.3M 而不是 445.1M，日志上只有参数量那一行能看出来。
   `tests/test_schedule.py::test_shape_overrides_win_over_the_common_table` 守这条。

### 预算与对照

445M 在这套自博弈管线下是 **49 步/分、7.9 局/s**（poly d256 是 577 步/分、
86 局/s），144k 步要 49 小时，所以这一轮只跑 **40,000 步**。

对照是 `v4-bf16-a40`：**日程与 qwen-bf16 逐字相同**（`--total-steps 40000
--lr-horizon-steps 40000 --lr-decay-steps 4400`、seed 1、bf16），差别只有骨干
—— poly d256（14.2M）对 qwen 形状 28 层（445.1M）。

没有它这一轮读不出结论：现有 poly 结果全在 111k/144k，直接比会把「换骨干」
和「预算小了 3.6 倍」混在一起。它是**从零重训**而不是分叉退火 —— v4-bf16 的
跑目录在收割清理时删了，只剩尺子那一个 `.pt`。这反而更对：qwen 本身就是从零
跑的，两边同起点才可比。

`v4-bf16-a40` 已跑满并收割（step 40189，loss 2.4044）。对上 BF16 尺子
（同架构、同 dim、跑到 11.1 万步）：

| | Elo | 直接对局 |
|---|---:|---:|
| `v4-bf16-111k`（尺子，11.1 万步） | 0.0 | 0.671 |
| `v4-bf16-a40`（4 万步） | **−123.6 ± 14.3** | 0.329 |

`runs/arena_budget-40k.json`。**这就是 4 万步预算本身的代价：123.6 Elo。**

### 但主判据不是等步数，是等时间

等步数比较对大模型是**严重放水**：

| | 参数量 | 速率 | 跑满 4 万步 |
|---|---:|---:|---:|
| `v4-bf16-a40` | 14.2M | 637 步/分 | **1.05 小时** |
| `qwen-bf16` | 445.1M | 48 步/分 | **13.82 小时** |

同样 4 万步，qwen 花掉 **13.2 倍**的机时。在这个基础上再补一个「步数代价」
只会把放水叠加一层 —— 曾经在这儿写过「净效果 = X + 123.6」，方向是反的。

换成等时间，判据反而更简单。上面的峰值表已经给了关键事实：
**BF16 poly 练到 111k 见顶，之后 5.6 万步一分不涨，178k 起开始真掉。**
111k 步在 637 步/分下是 **2.9 小时** —— 给 poly 13.8 小时，它第 2.9 小时就到顶，
剩下 10.9 小时用不掉。

所以 **poly 的「等时间最好成绩」就是 BF16 尺子本身**，判据是：

```
X > 0        X = qwen@4万 直接对上 v4-bf16-111k
```

不加 123.6。而且这条线**仍然偏袒 qwen** —— 它花 13.8 小时，poly 只花 2.9 小时。

`-a40` 对照仍然有用，但不是主判据：它量的是**每步效率**（同样 4 万次参数更新
哪种骨干学得多，对「再加计算量值不值」有参考价值），以及一条兜底线 ——
连只花 1/13 机时的 poly@4万 都打不过的话，这条路直接死了。

> **预期是负的。** 上一节刚测出「这套数据预算下约 30M 参数就是天花板」，
> 而 445M 是再翻 7.9 倍。但那条结论量的是**宽度**，换骨干换的是信息怎么在
> 格子之间流动（全注意力 vs 每 4 层一次注意力 + 深度卷积），不能直接推过来。
> 40k 步而不是 144k，就是为了让这个赌注便宜。

### 结果：两条判据都没过

`qwen-bf16` 跑满 40,207 步（loss 1.744、value 0.193、wdl 准确率 92.7%），
实际用时约 **13.8 小时**。三方对打见 `runs/arena_arch.json`
（3 对 × 1200 局、64 次模拟）：

| | 参数量 | 机时 | Elo |
|---|---:|---:|---:|
| `poly-111k`（BF16 尺子） | 14.2M | 2.9h | 0 |
| `poly-40k`（同日程对照） | 14.2M | 1.05h | −127.0 ± 12.2 |
| **`qwen-40k`** | **445.1M** | **13.8h** | **−247.7 ± 11.7** |

**主判据（等时间）：`X = −247.7 ± 11.7`。** qwen 花 13.8 小时，输给花 2.9 小时
的 poly，直接对局 0.189。

**兜底线（等步数）：`−120.7 ± 12.4`**（以 `poly-40k` 为基准重拟合，
直接对局 0.337）。**连只花 1/13 机时的 poly@4万 都打不过。**

兜底线这条尤其硬，因为等步数比较在**数据口径上对 qwen 几乎完全公平**：
`games_per_iter` 固定 2048，两边每 400 步都消化同样 2,048 局自博弈，
4 万步下来都是约 20.5 万局。**数据量一样、参数量多 31 倍、机时多 13.2 倍，
仍然输 120.7 分。**

两次白捡的复现校验：`poly-111k vs poly-40k` 这次 0.671，单独打的预算 arena
也是 0.671；`poly-40k` 这次 −127.0 ± 12.2，单独测是 −123.6 ± 14.3。

### 这个结论管到哪儿

**管得住的**：在本项目负担得起的任何预算下，Qwen3 形状的 445M 骨干明显更差。
这条可以直接用于决策 —— 别再往这个体量投。

**管不住的**：不能就此断言「全局注意力对 Blokus 没用」。两个未验证的前提：

1. **4 万步对一个从零初始化的 445M Transformer 可能太少。**
   注意这个反驳会**加深**等时间那条结论 —— 让它练够要更多小时，差距只会更大。
2. **学习率 5e-4 是按 1/宽度 从 poly 的 2e-3@256 推的**，而那条规律是在 poly
   骨干上量出来的，跨到 Transformer 上没有标定过。宽度实验里学习率没调对
   能差出 **180 Elo**（FP4、dim=384），所以这不是小事。

### 后续：`qwen-fp4`

FP4 唯一能改变结论的途径是**更快** —— 同样机时里跑更多步。同机实测
（`.121.17`，与 BF16 早期同迭代序号对比）：

| | 步/分 | 4 万步用时 |
|---|---:|---:|
| `qwen-bf16` | 51.1 | 13.8h |
| `qwen-fp4` | **91** | **7.4h** |

**1.78×。**（先前在 `.120.20` 上测到 1.40×，是跨机器比的 —— 那台对同一负载
慢 17~19%，稳态 37-39 对 45.8 步/分。跨机比速度这件事要当心。）

外推：同样 13.8 小时 FP4 能跑到约 7.5 万步，按 poly 的步数收益
（4 万 → 11.1 万 = +127 Elo）折算约值 +115，再倒扣量化噪声，**预计仍差约 150 分**。
`qwen-fp4` 正在跑 4 万步，用来把这个外推换成实测。

### 如果还要测「全局注意力」，换体量

别再用 445M。用 qwen 形状但**算力相当**的小模型 —— 8 层、hidden 512、
head_dim 64，参数量落在 **20~30M**，正好压在上一节测出的天花板附近，
速度能接近 poly。这样**等时间和等步数会重合成一个口径**，一次实验同时回答
两边，并且把「练太少」和「学习率跨架构没标定」这两个混淆项压到最小。

### `qwen-fp4` 的结果推翻了上面的预期：低精度在这里是正则化

`qwen-fp4` 跑满 40,198 步，用时约 9 小时。对上**同一把尺子、同样设置**
（`runs/arena_qwen-fp4.json`，1200 局、64 次模拟）：

| | 对 `poly-111k` 的直接得分率 | Elo |
|---|---:|---:|
| `qwen-bf16-40k` | 0.189 | −247.7 ± 11.7 |
| **`qwen-fp4-40k`** | **0.351** | **−106.8 ± 14.0** |

**FP4 比 BF16 好 141 分。同架构、同 445M、同样 4 万步，只差精度。**

四条线放在一起（都以 `poly-111k` 为锚）：

| | Elo | 机时 |
|---|---:|---:|
| `poly-111k`（BF16 尺子） | 0 | 2.9h |
| `qwen-fp4-40k` | **−106.8** | 9h |
| `poly-40k` | −127.0 | 1.05h |
| `qwen-bf16-40k` | −247.7 | 13.8h |

**兜底线翻过来了**：`qwen-fp4` 比 `poly-40k` 强约 20 分（BF16 版是输 120.7）。
**但主判据仍然是负的**：等时间口径下 qwen-fp4 花 9 小时，仍输给花 2.9 小时的尺子。

#### 机制：先前那个「容量税」的说法是反的

上一节把「FP4 加宽有收益而 BF16 加宽有损失」（+21.9 对 −24.2）解释成
**低精度的量化噪声是一笔容量税，加宽在赎回被税掉的有效容量**。这个说法
解释不了这里的 141 分 —— 这一轮 FP4 一步没多跑，收益不可能来自「赎回容量」。

更符合全部数据的解释是**反过来的**：**量化噪声在这里是正则化。**
这套数据预算下的容量天花板约 30M，445M 超配 15 倍；BF16 版本在噪声上过拟合，
FP4 的量化噪声把这件事压住了。**参数量越超配，这个效应越强** ——
在 dim=384（超配约 1.06 倍）上只值 46 分的摆幅，到 445M（超配 15 倍）就值 141 分。

这条改写也让 v5/v6 那组数读起来更顺：BF16 加宽是负的（超配后没有东西约束），
FP4 加宽是正的（噪声跟着规模一起起作用），而 FP4 从 384 到 512 归零 ——
因为正则化的收益已经追不上「数据不够」这个真正的瓶颈了。

> 这是**事后重新解释**，不是预先假设。要坐实它，最直接的一条是：
> 在同一个 445M 骨干上扫 dropout 或 weight decay，看纯正则化能否复现这 141 分
> 的一部分。没做之前，「FP4 在超配模型上是正则化」只是当前最省事的解释。

#### 这改变了下一步

先前写的「别再往这个体量投」要收回一半。**FP4 让 445M 从完败变成有戏**：
缺口从 247.7 收到 106.8，而且 FP4 只花 9 小时（BF16 要 13.8）。

在 BF16 那一轮的 13.8 小时预算里，FP4 能跑到约 6 万步。按 poly 的步数收益
（4 万 → 11.1 万 = +127）折算，4 万 → 6 万约值 +80，能覆盖现在这 106.8 的大半。
**这是第一次有理由认为换骨干可能真的能赢。**
