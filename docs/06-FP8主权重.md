# FP8 主权重

「模型主权重精度是 FP8」在本项目里是**字面意思**：权重张量本身就是 MXFP8
（E4M3 数据 + 每 32 个元素一个 E8M0 缩放），Blackwell 的张量核直接消费这个格式，
**不存在高精度 master 副本**。优化器每一步都是「反量化 → fp32 更新 → 随机舍入量化回去」。

实现落在 `cornerstone/fp8.py`：`fp8_linear()` 在 TE 的 `quantized_model_init`
上下文里创建 `te.Linear`，`Fp8AdamW` 负责更新。

## 为什么必须是随机舍入

E4M3 只有 3 位尾数，相对分辨率约 `2^-4`。**舍入到最近值时，凡是小于半个 ulp 的更新
都会被系统性地丢弃** —— 学习率一降，几乎所有更新都归零，训练直接停住。
随机舍入以正比于距离的概率向上/向下取整，期望值恰好是真值：偏差变成零均值噪声，
而噪声可以靠大 batch 压，偏差压不掉。

单测 `test_tiny_updates_survive_only_with_stochastic_rounding` 直接把这件事测出来：
对 0.1 附近的权重（ulp = 0.0078125）反复施加 `delta = 1e-4`（约 1/78 个 ulp）300 次，

- 确定性舍入：权重**一动不动**
- 随机舍入：移动量达到理论值 `300 × delta` 的一半以上

## 五个踩过的坑（其中一条我最初判断错了）

### 一、量化前不能过 bf16

最早 `write_weight_` 写成 `param.quantize_(src.to(param.dtype))`，而 `param.dtype`
是 bfloat16。结果随机舍入**完全失效**，权重几乎不动，但从代码上一点看不出问题。

原因：bf16 在 0.1 附近的 ulp 是 `4.9e-4`，而抖动后「该向上进位」的窗口只有约 `1e-4` 宽。
更糟的是 bf16 的格点 `0.10546875` **恰好就是相邻两个 e4m3 格点的中点** ——
整条窗口被 bf16 塌到中点上，再按 round-half-to-even 倒回原值。

改成直接送 fp32 进 `quantize_` 就好了。这类 bug 不写「小更新能不能存活」这条测试
是发现不了的：loss 还在降（其他非量化参数在学），只是慢得离谱。

### 二、MXFP8 要求两个维度都被 32 整除

这条会一路传导到 batch size 上：主干的 token 维是 `B × 196`，而 `196 mod 32 = 4`，
所以 **B 必须是 8 的倍数**。自博弈里 `prepare()` 返回的批大小随局面数变化，
所以 `CornerNet.forward` 在 FP8 模式下会把 batch 补齐到 8 的倍数、算完再切回来。

### 三、每参数 2.06 字节 —— 比纯 BF16 多，但比真实基线省

TE 同时保留**行布局与列布局两套数据**（反向的两个 GEMM 需要不同的连续维，
而块缩放的 FP8 没法便宜地转置），每个参数是 `2 × (1 + 1/32) ≈ 2.06` 字节。

对着**纯 BF16 存储**（2 字节）确实略多。但项目里真实的对照不是它 ——
非 FP8 配置走的是标准混合精度：**主权重是 fp32**（4 字节/参数），
`autocast` 只在计算时临时转 BF16。对着那个基线，FP8 是实打实省显存的：

| dim=256 blocks=16 | BF16 配置 | FP8 配置 | 省 |
|---|---:|---:|---:|
| 权重 | 56.7 MB | 33.9 MB | 40% |
| 权重 + 优化器状态 | 239.8 MB | 126.8 MB | 47% |

（优化器那一项还叠加了另一个差异：`Fp8AdamW` 的动量用 BF16 存，
`AdamW` 用 fp32。两者都不是「权重」，约束不适用。）

### 四、FP8 与 `torch.compile` 不能同时用

开着 `torch.compile` 跑 FP8，先冒出 TE 自定义算子的 graph break 告警，
接着编译出来的图直接 **CUDA 非法访存**。两者只能二选一。

代价不小：`torch.compile` 在这个模型上值 1.8×（见 [07](07-性能调优.md)），
FP8 跑等于连这一截也一起放弃。`TrainConfig.resolve()` 里会自动关掉 compile 并打印提示。

### 五、调用 TE 时，当前 CUDA 设备必须与张量设备一致

在 cuda:0 建好模型再在 cuda:1 建第二份，第二份的前向会报
`cublas_gemm: the function failed to launch on the GPU`。
报错点还离根因很远 —— 最初表现为注意力里 cuDNN 的 `mha_graph.execute` 失败。

**一开始把这归因成「同进程只能用一张卡」，是错的。** 真正的原因是
TE 按**当前 CUDA 设备**取 cuBLAS 句柄：张量在 cuda:1 而当前设备是 cuda:0 就会炸。
把前向包进 `torch.cuda.device(dev)` 之后，两张卡上的 FP8 模型在同一进程里并行工作完全正常。

而且这条不匹配有**两种**表现，都难查：

- 有时**静默退回非量化计算**，只发一条 `You are using quantized weights without
  quantized compute` 的 UserWarning —— 模型看着在训练，FP8 已经名存实亡
- 有时**直接 CUDA illegal memory access**，报错点还常常飘到别的算子上

这两种表现我都撞过：先是那条一直找不到源头的警告，后来 A/B 实验把 FP8 放到 cuda:2
（训练步没设当前设备）直接崩掉。

所以护栏最终放在 **`CornerNet.forward` 里**，而不是逐个调用点打补丁 ——
训练步、自博弈、评测、Web 推理、checkpoint 读写有五六条路径，
漏掉任何一条都会以上面两种形态之一炸出来。
`torch.cuda.device` 是线程局部的，多卡多线程各设各的互不干扰。
回归测试 `test_fp8_model_works_when_current_device_differs` 专门守这条。

两个教训：

1. **「A 和 B 一起用会炸」不等于「A 和 B 不能一起用」。** 先找准触发条件再下结论 ——
   我因为这个误判给 FP8 加了半天的单卡护栏。
2. **一个失效模式有两种表现时，只修看得见的那种是不够的。**
   崩溃会自己暴露，静默降级不会。

综合看，FP8 唯一真正付出的性能代价是第四条（用不了 `torch.compile`，约 1.8×）。

## 实测吞吐：FP8 的收益比预期小得多

| dim | blocks | 参数 | BF16 局面/s | FP8 局面/s | 加速比 |
|---:|---:|---:|---:|---:|---:|
| 256 | 16 | 14.2M | 28,579 | 28,452 | 1.00× |
| 512 | 16 | 56.3M | 13,599 | 13,961 | 1.03× |
| 768 | 16 | 126.3M | 8,558 | 9,011 | 1.05× |
| 1024 | 12 | 169.6M | 8,011 | 8,476 | 1.06× |

预期是约 2×，实测只有 1.00–1.06×。原因：

1. **每层的量化开销**。MXFP8 每 32 个元素一个缩放因子，每层都要对激活重新扫一遍
   求块 amax 再量化。序列只有 196 个 token，GEMM 本身不够大，这笔固定开销摊不薄。
2. **模型不是纯 GEMM**。深度可分离卷积、RMSNorm、注意力、以及 17836 维的策略头输出
   都不走 FP8，它们在总时间里占比不低。
3. D=256 时更是**核函数启动受限**：单次前向约 10 ms，和批大小几乎无关。

结论：FP8 主权重这条路**正确、可用、省显存**（数值与显存都有测试守着），
但在这个规模和这种结构上它**不是吞吐杠杆**：算得不比 BF16 快，
还因为和 `torch.compile` 不兼容而净亏约 1.8×。
真想提吞吐，优先级是 `torch.compile` 融合 + CUDA Graph + 加宽模型。

## BF16 对照实验

方案里写死了一条：**没有 BF16 对照，「FP8 无损」就是没有依据的说法。**

```bash
bash scripts/ab_experiment.sh start
bash scripts/ab_experiment.sh status
bash scripts/ab_experiment.sh compare 20000     # 在对齐步数处头对头
```

### 对照实验最容易被什么破坏

做这个对照时，下面几件事任意一件都足以让结论作废，而且都不会报错：

1. **两条的 `games_per_iter` 不同**。相同 step 下一方看到的新自博弈数据更少 ——
   而数据量是 AlphaZero 类训练的主导因素，这个差异会盖过精度带来的差异
2. **中途崩溃导致 replay 快照丢失**，buffer 从零重建
3. **只保留最近 K 份 checkpoint**，早期的被删掉之后，
   连「在同一步数处头对头」都做不到
4. **超参表被抄了第二份**。守护脚本原先自己拼了一整套启动参数，
   于是同一套配置存在两个地方。它只在**开发机过期后自动恢复**时生效，
   所以一旦两处不同步，实验会从某次恢复开始悄悄变成另一个实验，
   日志上完全看不出来 —— 而恢复正是最不容易被人盯着看的时刻。
   现在守护脚本转调 `ab_experiment.sh start-a/start-b`，配置只有一份。

判断对照是否成立有个简单的自检：**换一种对齐方式（按 step / 按累计对局数），
结论是否翻转。** 会翻转就说明它测的不是精度，是别的东西。

### 更根本的一点：跨实验比 loss 不可靠

策略目标是**网络自己的 MCTS 搜索结果**。网络变强 → 搜索出的目标更尖锐 →
可达到的 loss 随之改变。所以两条曲线的 loss 高低**不直接对应棋力**，
低 loss 也可能只是「更擅长预测自己的搜索」。

**结论只认头对头胜负**（`tools/compare_nets.py`），不认 loss 曲线。

### 锁死的控制变量

`scripts/ab_experiment.sh` 把上面这些坑一次性堵掉：

- 除 `--fp8` 与设备外，全部配置逐字相同，种子相同，都从零开始
- **两边都关掉 `torch.compile`**。它会改变算子融合与数值细节，
  留着它 BF16 就多了一个变量；关掉后两边墙钟速度也变得可比
- 每 10000 步留一个永久里程碑 checkpoint，供后续在对齐步数处头对头
- 两条腿的**卡数必须一致**，否则每卡的并行局数不同，又多一个变量

### 两台机器，一边一条

有两台开发机之后，两条腿各独占一台，各用满 4 张卡、128 个引擎线程：

```bash
# 机器 1
A_DEVICES=cuda:0,cuda:1,cuda:2,cuda:3 ENGINE_THREADS=128 bash scripts/ab_experiment.sh start-a
# 机器 2
B_DEVICES=cuda:0,cuda:1,cuda:2,cuda:3 ENGINE_THREADS=128 bash scripts/ab_experiment.sh start-b
```

对称性没有被破坏：两边卡数、线程数、超参全都相同，只有 `--fp8` 不同。
比起挤在一台机器上各占两张卡，好处是两条腿不再抢 CPU ——
自博弈是 CPU/GPU 流水，共用一台时 128 个核要分给两条腿，
它们的引擎线程会互相挤，而挤的程度取决于两边的进度，是个**不受控的变量**。

代价是多了一条硬约束：`runs/` 在共享 NFS 上，
**同一条实验绝不能在两台机器上同时跑**，否则 checkpoint 互相覆盖。
机器与实验的绑定写在 `.devhosts`（不进 git），守护脚本按表办事，不会自作主张换机器。
