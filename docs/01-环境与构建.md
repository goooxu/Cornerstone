# 环境与构建

## 目标平台

本项目的代码与调参都针对下面这类配置。换平台时先跑 `scripts/probe.sh` 重新确认，
并按实测值调整并行度。

| 项 | 值 | 对设计的影响 |
|---|---|---|
| CPU | 2× Grace（Neoverse-V2），144 核，1 线程/核 | **aarch64**：引擎不能用 AVX，只写可移植位运算 + GCC builtin |
| NUMA | node0 = 核 0–71，node1 = 核 72–143 | 自博弈 worker 按 NUMA 分组，各喂本地的 GPU |
| GPU | 4× Blackwell，**compute cap 10.0**，各 185 GB HBM3e，NV6 全互联 | sm_100 原生支持 **MXFP8**，主权重可以「存储格式即计算格式」 |
| 内存 | 956 GB | replay buffer 可以大量常驻内存 |
| 页大小 | 64 KB | 共享内存环形缓冲的分配要按此对齐 |
| 工作目录 | 网络盘，容量吃紧 | replay 热数据放本地盘，快照回写工作目录 |
| 本地盘 | `/tmp` 在本地 NVMe 上，容量充裕 | 热数据落这里 |

> 原计划把热数据放 `/raid`，实测该目录是 root 属主、普通用户写不了。
> `/tmp` 同样在本地 NVMe 上、容量充裕，且项目规范明确允许使用，于是改用 `/tmp/cornerstone`。
> tmpfiles 的清理策略是 30 天龄期，活跃写入的文件不会被清掉；热数据本身也可再生。

## 容器

宿主机只有 git 和 g++，cmake / nvcc / torch 全在容器里，所以**任何编译和训练都必须进容器**。

```bash
bash scripts/devbox.sh up             # 幂等，已在跑就什么都不做
bash scripts/devbox.sh exec <cmd...>  # 以当前用户身份在容器内执行
bash scripts/devbox.sh root <cmd...>  # 以 root 执行（装系统包用）
bash scripts/devbox.sh shell          # 交互 shell
bash scripts/devbox.sh status / down
```

容器参数里几个不是随便加的：

- `--user $(id -u):$(id -g)`：工作目录在网络盘上，网络盘通常有 root_squash。以 root 跑会产生
  属主错乱甚至写不进去的文件。
- `-e HOME=<repo>/.container-home`：pip 装的包落在工作目录内，容器重建后还在。
- `-e USER=cornerstone -e LOGNAME=cornerstone`：容器里没有本机的 LDAP 用户，
  `getpass.getuser()` 会因为 `pwd.getpwuid()` 找不到 uid 而抛异常 ——
  torch 的一些缓存路径逻辑正好会调它。给个固定值就绕过去了。
- `-e TRITON_CACHE_DIR / TORCHINDUCTOR_CACHE_DIR` **指向本地盘**：
  编译会写大量小文件，留在网络盘的 HOME 里会让 `torch.compile` 慢到不可接受。
  缓存丢了只是重编译，不影响正确性。
- `--ipc=host`：默认 `/dev/shm` 只有 64 MB，自博弈的共享内存不够用。
- `--network host`：Web 试玩工具直接暴露端口，省掉端口映射。
- `--cap-add SYS_NICE`：给自博弈线程做 CPU 绑核与优先级调整。
- `--init`：见下。

脚本里的路径全部由脚本自身位置推出，不写死绝对路径——换机器、换用户都不用改。

### `--init`：不加就会漏显存

容器的入口是 `sleep infinity`，它是 PID 1 却**不会 `wait()` 回收子进程**。
训练进程退出后就一直挂成僵尸，而**僵尸进程的 GPU 上下文不会被释放**。

实际现象是这样的：`train.sh status` 说没在训练，`ps` 里也找不到 train.py，
但 `nvidia-smi` 显示 47 GB 显存被占着，占用者是一个查不到命令行的 PID。
顺着 PPID 一路查上去才看到：

```
721729  4126351  Z   [python3] <defunct>
4126351 4126327  Ss  sleep infinity          <- 容器 PID 1，从不 wait()
```

这时候新训练要么起不来，要么只能挤在剩下的显存里跑，
而**故障表现（显存不够）离根因（PID 1 不回收子进程）非常远**。

加 `--init` 让 docker 塞一个 `docker-init`（tini）当 PID 1，僵尸自动被回收。
容器重建后 47 GB 立刻回到 3 MiB。

判断加没加：

```bash
docker exec cornerstone ps -o args --no-headers -p 1
# 期望看到 /sbin/docker-init -- ...
```

改这个参数要**重建容器**（`down` 再 `up`），`docker run` 的参数改不了。

## 容器内实测的软件栈

| 组件 | 版本 |
|---|---|
| CUDA (nvcc) | 13.3 |
| PyTorch | 2.13.0a0（NGC 26.07） |
| Transformer Engine | 2.17.0 |
| Triton | 3.7.1 |
| pybind11 | 3.0.4 |
| cmake / ninja | 3.31.6 / 1.13 |
| g++ | 13.3.0 |
| numpy | 2.1.0 |

FP8 能力确认（这是「主权重 FP8」方案能否落地的前提）：

- `torch.float8_e4m3fn` / `torch.float8_e5m2` 均可用
- TE 提供 `MXFP8BlockScaling`、`Float8BlockScaling`、`Float8CurrentScaling`、`NVFP4BlockScaling` 等 recipe
- **`transformer_engine.pytorch.is_mxfp8_available() -> True`**

需要额外装的（不在镜像里）：`pytest`、`fastapi`、`uvicorn[standard]`，用 `pip install --user` 装到
`HOME`（即工作目录内），容器重建不丢。

## 构建

```bash
bash scripts/devbox.sh exec bash scripts/build.sh
```

CMake 里两点值得说明：

- 优先探测 `-mcpu=native`，退回 `-march=native`，都不支持就不加。写死 `-march=native`
  在 aarch64 上会直接编译失败。
- pybind11 用容器里 python 侧自带的那份（`pybind11.get_cmake_dir()`），不额外拉源码。

产物 `_engine.cpython-312-aarch64-linux-gnu.so` 直接落到 `cornerstone/` 包目录，
装不装包都能 `import cornerstone`。

## 环境探测

`scripts/probe.sh` 宿主机和容器内都能跑，输出 CPU/NUMA/GPU/工具链/FP8 能力/磁盘的完整报告。
换机器后第一件事就是跑它，确认新机器的参数。
