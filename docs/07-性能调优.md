# 性能调优

目标是「压满 CPU 与 GPU」。过程中瓶颈换了三次位置，每次都得先量出来在哪，再动手。

## 起点

最初的自博弈只有 **7,508 次网络评估/s**，`GPU 占墙钟 81%`。
看上去像 GPU 不够快，但把批量从 256 加到 1024 只提升 8% —— 算力受限的话不会这样。

C++ 侧早有结论：单纯的着法生成在 128 线程下能跑到 **1030 万次/s**，
不可能是瓶颈。所以问题在 GPU 侧的**固定开销**：D=256 的模型很瘦，
16 个 block 摊下来每次前向上百次 kernel launch，单次前向约 10 ms 且与批大小几乎无关。

## 三步优化

测量条件：14.2M 参数（dim 256 / blocks 16），64 次模拟/手，单卡。

| 配置 | 评估/s | 等效局/s | GPU 占比 | 单次前向 |
|---|---:|---:|---:|---:|
| 基线（eager，引擎单线程，并行 1024） | 13,442 | 7.8 | 0.65 | 49.7 ms |
| + `torch.compile` | 24,513 | 14.1 | **0.38** | 16.1 ms |
| + 引擎 32 线程 | 47,931 | 27.6 | 0.74 | 15.8 ms |
| + 并行局数 2048 | **56,859** | **32.8** | **0.83** | 29.8 ms |

单卡合计 **4.2×**，GPU 利用率从 0.65 提到 0.83。

### 一、固定批大小

`prepare()` 返回的批大小是变的。若照实际数量切片喂进去，`torch.compile`
会为**每个出现过的形状**重新编译（单次约 60 s）。改成每次都按固定批跑、
多余的行算完丢掉——实测批均本来就占并行局数的九成以上，这点浪费远小于重编译。

顺带解决了两件事：MXFP8 要求 batch 是 8 的倍数；以及后续上 CUDA Graph 需要静态形状。

补齐用的缓冲区必须 `zeros` 而不是 `empty`：`empty` 可能是 NaN，
一旦通过 RMSNorm 之类的规约算子传染到整批，就查不出来了。

### 二、torch.compile

1.82×。纯粹是把上百个小 kernel 融合掉——正是「启动受限」的对症解法。
首次编译约 60 s，之后形状固定就不再重编。

**但它把瓶颈推到了另一侧**：GPU 占比从 0.65 掉到 0.38，
也就是说 62% 的墙钟时间花在了 C++ 的树搜索上，而那是单线程的。

### 三、引擎多线程

各局的搜索树完全独立，`prepare` / `feed` / `advance` 按局分段并行即可。
单卡上 32 线程给出 1.96×，GPU 占比回到 0.74。

> ⚠️ **这个 32 是单卡结论，多卡上它正好是最差的一档。**
> `parallel_games()` 和 `feed()` **每次调用都现建现销 `std::thread`**，不是常驻池，
> 于是线程数一多，spawn 开销就压过并行收益。单卡上 32 只比 8 差 10%，
> 4 卡上却差 **1.81×**：
>
> | 线程/卡 | 总线程 | 4 卡评估/s | |
> |---:|---:|---:|---|
> | 4 | 16 | 170,407 | 每线程 256 局，并行度不够 |
> | **8** | **32** | **180,554** | **最优** |
> | 16 | 64 | 166,017 | |
> | 32（曾经的默认） | 128 | 99,815 | |
>
> 曲线在每卡 6~8 之间是平的，两侧都掉。配置项因此改名成
> **`engine_threads_per_gpu`，默认 8** —— 单位写进名字里。
> 它原先叫 `engine_threads`、语义是"总数、多卡均分"，而上面那个"32 线程最优"
> 是**单卡**基准测的（单卡下总数就等于每卡），照抄成多卡的每卡值就是 128 总数，
> 正好是最差的一档。两个前提：最优点绑在**每卡并行局数**上
> （这里 1024），`parallel_games` 一改就要重测；根治办法是把 `std::thread`
> 换成常驻线程池，那之后这条曲线会变平、配置也就不再敏感。

这里有条硬要求：**多线程的结果必须和单线程逐位一致**。
批要按局号顺序合并（否则 `feed()` 里 logits 和局对不上），
每线程要有自己的 scratch。有单测 `test_engine_threads_do_not_change_results`
对着法序列、策略目标、比分逐一比对——这类竞态的表现是「训练效果变差」而不是崩溃，
不测出来根本发现不了。

## 多 GPU

`cornerstone/multigpu.py`：每张卡一份模型副本 + 一个独立驱动，用 Python 线程并发。

线程能真正并行，是因为两段热点都放开了 GIL：C++ 引擎全程 `gil_scoped_release`，
torch 下发 CUDA 内核时也不持有 GIL。

训练循环是**同步**的（自博弈与训练轮流跑），所以自博弈阶段把 4 张卡全用上、
训练阶段回到主卡，没有哪张卡会闲着。权重每轮同步一次到各副本 ——
自博弈用上一轮的权重，在 AlphaZero 类算法里本来就是常态。

| 配置 | 评估/s | 等效局/s |
|---|---:|---:|
| 单卡（并行 2048） | 56,859 | 32.8 |
| **4 卡（共 8192 局）** | **170,715** | **98.4** |

4 卡相对单卡 3.0×（约 75% 并行效率，Python 线程调度是主要损耗）。
**相对最初的 7,508 评估/s 合计 22.7×。**

两个必须串行的地方：

- **编译**：`torch.compile` 的编译期有全局状态，多线程并发编译会直接报错
  （表现为 Dynamo 内部的 weakref 异常）。构造驱动时逐卡串行预热，之后才起线程。
  4 卡串行预热约 98 s。
- **编译缓存要放本地盘**。inductor/triton 编译会写大量小文件，
  把 `TRITON_CACHE_DIR` / `TORCHINDUCTOR_CACHE_DIR` 留在网络盘上的 HOME 里，
  编译慢到不可接受。缓存丢了只是重编译，不影响正确性，所以放 `/tmp` 是划算的。

## FP8 不在这条优化链上，但也不再拖后腿

见 [06](06-低精度训练.md)：MXFP8 实测只有 1.00–1.06×。
每层都要重扫激活求块 amax，196 个 token 的 GEMM 摊不薄这笔开销。
FP8 是项目的**功能要求**，不是性能手段。

但「FP8 用不了 `torch.compile`，所以净亏 1.8×」这条**范围记宽了**：
真正的限制是 FP8 不能**整模型**编译（会把 TE 的全局 FP8 上下文编进图里，
多卡下段错误），按 block 编译则没问题，实测 37.49 → 15.97 ms。
详见 [06](06-低精度训练.md) 第四条。

## 验收

```bash
bash scripts/devbox.sh exec python3 tools/bench_selfplay.py \
    --parallel 1024 2048 --compile --engine-threads 8
bash scripts/devbox.sh exec bash scripts/monitor.sh 15
```

`monitor.sh` 优先从常驻的 dcgm-exporter 抓 GPU 指标（比反复起 nvidia-smi 便宜），
抓不到就退回 nvidia-smi；CPU 侧有 mpstat 用 mpstat，没有就自己读 `/proc/stat` 算。

## 训练步：唯一没吃到 compile 的热点

`torch.compile` 长期只包了自博弈的前向（`SelfPlayDriver.fwd`），**训练步一直是 eager**，
而它占（修掉评测那个 bug 之后）墙钟的四成。

按模块拆开看（dim=256，batch=1024，eager 前向 36.4 ms）：

| 模块 | 耗时 | 占比 |
|---|---:|---:|
| SwiGLU | 20.5 ms | **74.0%** |
| DepthwiseSpatial | 5.0 ms | 18.1%（FLOPs 不到 2%） |
| Attention | 1.5 ms | 5.5% |

再往里一层，SwiGLU 的两个 GEMM 加起来只有 0.27 ms，而 `silu(g)*v` 一个逐元素算子就占
0.96 ms —— 因为 `h.chunk(2, -1)` 给出的是**非连续视图**，PyTorch 退回非向量化的
逐元素核，只跑到 1.28 TB/s（连续张量能到 3.73）。

三种解法都实测过，**只编译 SwiGLU 子模块最好**：

| 做法 | 训练步 BF16 | 训练步 FP8 | 自博弈前向 | 改 checkpoint |
|---|---:|---:|---:|---|
| 原样 | 101.1 ms | 106.1 ms | — | |
| 整模型 compile | 89.8（1.13×） | 98.8（1.07×） | — | 否 |
| 拆成 gate/val 两个 Linear | 81.4（1.24×） | 87.1（1.22×） | FP8 **慢 15%** | **是** |
| **只编译 SwiGLU** | **73.1（1.38×）** | **79.4（1.34×）** | 中性 | 否 |

整模型 compile 反而不如只编译热点：带 autograd 时前向必须为反向保存中间量，
融合空间比推理路径小得多。拆两个 Linear 在 FP8 下等于把同一个输入量化两次、
跑两个更小的 GEMM，自博弈那边是负收益。

实现上必须用 `nn.Module.compile()` **原地**编译。写成 `blk.mlp = torch.compile(blk.mlp)`
会返回 `OptimizedModule`，把 state_dict 的键变成 `..._orig_mod...`，当场破坏
checkpoint 契约（实测多出 32 个键）。有单测守着。

## 还没做的

- **CUDA Graph**：~~形状已经固定，是顺理成章的下一步~~ ——
  **优先级应该降低**。那条推理的前提是前向受核函数启动限制，而实测编译后的前向
  随批**线性**（256→4096 每翻倍 1.90–2.03×，吞吐恒在 74k 局面/s），
  启动开销早被 `torch.compile` 吃掉了，CUDA Graph 没多少可拿
- **异步自博弈**：现在自博弈与训练严格轮流。拆成独立进程让两者重叠，
  理论上还能再拿一截，代价是引入权重版本管理
- **单局面搜索的批量化**：Web 试玩每次模拟只有 batch 1，
  要靠 virtual loss 在单棵树里并行展开若干叶子才能压下延迟
