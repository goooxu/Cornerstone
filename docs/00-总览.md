# 总览

## 为什么是这个设计

项目的四条硬约束各自把设计逼向一个方向：

| 约束 | 推出的结论 |
|---|---|
| 不用棋谱 | 只能自博弈强化学习。连**评测基线**也必须由规则构造（随机 / 贪心 / 纯 rollout MCTS），不能拿棋谱当测试集 |
| 不复用开源 Blokus AI 结构 | 网络结构自研。常见开源实现是卷积 ResNet，我们走「FP8 GEMM 为主体」的路子，天然分道 |
| FP8 混合精度 | GEMM 输入走 MXFP8（前向 E4M3 / 反向 E5M2），主权重与优化器状态保持 fp32。**必须有 BF16 对照跑**，否则「FP8 无损」没有依据 |
| 压满 CPU 与 GPU | CPU 跑 MCTS 与着法生成，GPU 跑批量推理与训练，用共享内存攒批把两者流水重叠 |

## 关键设计决策

### 动作空间 = 91 × 196 = 17836

21 枚棋子按「4 旋转 × 2 镜像」展开去重后恰好 **91 个不同朝向**（生成时会断言这个数）。
动作编码为 `orientation * 196 + 包围盒左上角格号`，正好对应策略头的 `91×14×14` 张量。
越界与非法动作用 mask 屏蔽。

### 价值头是 WDL 三分类，不是 tanh 标量

本项目的胜负判定是「占格多者胜、相同为和局」，和局是**真实且不罕见**的结果——
随机对局下和局率约 4.5%，强度接近的对手之间只会更高。
tanh 标量没法区分「这是和棋局面」和「胜负各半的混沌局面」，所以价值头用 WDL 三分类 softmax，
MCTS 回传用 `P(W) − P(L)`。

### 特征里不放手数 ply

见 [docs/02-引擎设计.md](02-引擎设计.md) 的对称群一节：`ply` 的奇偶性和座位相关，
会让 ROT180 / ANTIDIAG 两个增广产生分布外样本。改用座位无关的「己方/对方占格数」，
信息量不比 ply 少，且四个对称变换全部严格自洽。

### FP8 在本项目里既不省显存也不提吞吐

实测（详见 [06](06-低精度训练.md)）：

- **不省显存**：两条腿都是 16 字节/参数（计算权重 2 + 梯度 2 + fp32 master 4 +
  fp32 m/v 8）。激活侧同理 —— 峰值由 SwiGLU 的 hidden 主导，那部分本来就是 bf16
- **不提吞吐，实际是负的**：微基准里 D=256 时 1.00×、加宽到 169M 参数也只有 1.06×；
  而端到端两条 15 万步长跑实测，FP8 的**训练步慢 1.40×、自博弈慢 1.13×**。
  MXFP8 每层都要重扫激活求块 amax，196 个 token 的 GEMM 摊不薄这笔开销 ——
  批越小摊得越差，所以训练步（每卡 256）比自博弈（批 920）吃亏更多
- ~~还净亏一截：FP8 与 `torch.compile` 不兼容~~ —— 这条**范围记宽了**：
  FP8 不能整模型编译（多卡下段错误），但**按 block 编译没问题**，
  前向实测 37.49 → 15.97 ms。两条腿现在都吃得到 compile

所以 FP8 是一条正确、可用、有数值保障的路，但在这个规模和这种结构上
**它不是杠杆** —— 既不是显存杠杆也不是性能杠杆。
要提吞吐得靠 `torch.compile` 融合、CUDA Graph。

~~加宽模型也是一条路~~ —— **这条要收回**。[06](06-低精度训练.md) 里那张宽度表
是实测的：dim 256→512 自博弈吞吐从 28,579 掉到 13,599 局/s（**掉 2.1 倍**），
而 FP8 只补回 1.03×；一直加到 169.6M 参数也只有 1.06×。
整机层面永远是**核函数启动受限** —— 注意力、深度卷积、各 RMSNorm、三个头
都留在 bf16，GEMM 那点收益被稀释掉。单个 `te.Linear` 在 K=4096 时 FP4 确有
2.03×，但那对应 `dim≥4096`，与本项目的规模差一个数量级。
**「加宽之后低精度就回本了」在这张表面前站不住。**

> 早先的 FP8 主权重方案（权重直接以 MXFP8 存储、无 fp32 副本）确实省显存
> —— 权重 −40%、含优化器状态 −47%。但它违反「主权重始终 fp32」这条原则，
> 已经移除；显存收益随之消失。

## 当前训练

`v2-bf16` / `v2-fp8` 是 FP8 与 BF16 的受控对照（协议见 [06](06-低精度训练.md)）。
除 `--fp8` 外全部超参逐字相同、种子相同、初值逐位相同、都从零开始，各跑满
**150,000 步**。棋力结论以**头对头胜负**为准 —— Elo 是相对的，两场独立拟合的
数字不能相减。

- **`v2-bf16`**：150,227 步 / 4.42 小时 / 纯策略峰值 1522.6 Elo（第 12 万步）。
  结构、训练方法、训练过程与棋力评测见 [BF16 训练报告](../reports/BF16训练报告.md)。
- **`v2-fp8`**：150,234 步 / 5.93 小时 / 纯策略峰值 1609.8 Elo（第 11 万步）。
  见 [FP8 训练报告](../reports/FP8训练报告.md)。
- **A/B 结论：FP8 +27.7 Elo [+15.4, +39.7]**（两边各取最强的 4 档交叉对打
  6,400 局，16 对赢 14 对）。但 27.7 分与「同一条腿从峰值训到终点」的损耗
  （19~22 分）是同一量级，所以读作「看不出 FP8 的精度代价」而非「FP8 更好」；
  而 FP8 的训练步慢 1.40×、显存零收益。
- 两条腿都在训练量的 **73~80%** 处见顶，之后净损耗 19~22 分 ——
  「训练越久越差」是比精度选型更优先的问题。

## 已完成部分的实测数据

### 引擎吞吐（随机对局，全程 C++、释放 GIL）

| 线程 | 对局/s | 着法生成/s |
|---:|---:|---:|
| 1 | 3,165 | 85,810 |
| 16 | 50,252 | 1,362,863 |
| 64 | 201,874 | 5,474,436 |
| 128 | 380,458 | 10,319,128 |

128 线程相对单线程加速比 **120×**（约 94% 并行效率）。

含义：着法生成不会是瓶颈。按 200 次模拟/手估算，CPU 侧能支撑的搜索量远超 GPU 侧
能提供的推理吞吐——瓶颈落在 GPU，这是正确的位置。

### 随机对局的统计特征

- 平均每局 **27.1 手**（远小于上限 42 手，说明随机走子很早就把自己堵死）
- 先手胜率 **0.541**，和局率 **0.045**
- 平均占格数：先手 55.1 / 后手 53.4（满分 89）

随机对局下先手优势只有 4 个百分点，但**随棋力放大** —— 强网络下实测 25 个
百分点（配对口径实测 0.73~0.77，见 [08](08-已知问题与后续.md)）。arena 评测必须交换先后手。

### 正确性

- 规则单测 146 项全绿
- 与**完全独立的朴素实现**交叉比对 **1,000,020 个局面，零不一致**（耗时 192.6s）

### 续训（真的停了再起，不是纸面推演）

开发机每 8 小时过期一次——容器被回收，训练进程随之消失且**来不及优雅收尾**。
所以续训不是可选项，丢多少进度完全取决于 checkpoint 频率。
实测一次落盘只要 0.1–0.14 秒（约 170 MB：fp32 主权重 + fp32 一阶/二阶动量，两条腿相同），
相对一轮 42 秒仍可忽略，因此设成**每轮都落盘**，丢失量上限就是一轮。

这条路径演练暴露了四个真问题，都已修：

1. **SIGTERM 不触发收尾落盘**。最终的 checkpoint + 快照只在主循环正常退出时执行，
   信号直接把进程打断了。改成协作式停止标志，自博弈与训练循环都会检查。
2. **快照丢了会导致过拟合**。续训时若 replay 快照缺失，buffer 从零重建，
   却照样跑满每轮的训练步数 —— 等于在几万个局面上反复训练几十遍。
   **loss 会明显变好看，但那是坏了。** 加了按数据量限流的 `steps_for_iteration()`。
3. **「每 N 步落一次盘」不能写成 `step % N == 0`**。早期按数据量限流会让步数
   错位（19832 而不是 20000），取模条件从此永远不成立，只剩时间触发在起作用。
   这个 bug 有三个孪生兄弟：checkpoint 触发、里程碑保留、对照实验找对齐 checkpoint，
   全都因为同一个假设（「步数会落在整数倍上」）而失效。
   改成记录「距上次落盘的步数」。
4. **写快照不是原子的**。进程写到一半被强杀会留下半截 npz，
   下次续训崩在 zlib 解压上 —— 而且崩在「恢复」这一步，
   等于把还完好的 checkpoint 一起废掉。改成临时文件 + 原子重命名，
   并且让 `resume()` 容忍坏快照（模型照常恢复，replay 重新攒）。

还有一条是跑满之后才暴露的：**守护脚本必须知道「训练完成」和「训练挂了」的区别**。
跑满 `total_steps` 之后，训练进程一启动就发现 `step >= total_steps`，
落一份 checkpoint 加几百 MB 的 replay 快照然后退出；守护看它没在跑，
3 分钟后再拉一次 —— 白烧 NFS，日志还会被「恢复失败，下一轮重试」刷满，
而它根本不是失败。现在守护会比对 metrics 里的最新 step 和
`ab_experiment.sh` 里的 `--total-steps`（不在守护里再抄一份），
跑满就记一条日志然后停手。

修完之后，停止会打印「收到信号 → 按请求停止 → 已落盘」，
重启则打印「已从 checkpoint 恢复：step / iter / replay 局面」——
模型、优化器状态、步数、轮次、RNG、replay 全部接上。

### 自博弈吞吐（14.2M 参数，64 次模拟/手）

| 配置 | 评估/s | 等效局/s |
|---|---:|---:|
| 最初 | 7,508 | 4.3 |
| 单卡（compile + 引擎 8 线程/卡 + 并行 1024） | 56,859 | 32.8 |
| 四卡 / 多线程 | 170,715 | 98.4 |
| **四卡 / 每卡一进程** | **187,856** | **108** |

合计 **25×**。瓶颈换过三次位置，过程见 [docs/07-性能调优.md](07-性能调优.md)。
`v2-bf16` 那次 15 万步长跑里的实际稳态是 **176,316 评估/s、96.7 局/s**
（比基准低一点，因为长跑里还夹着入库与落盘）。

FP8 曾经在这里完全不扩展（4 卡 39k，还不如 2 卡），根因是同进程内的 GIL 与
TE 全局 FP8 状态争用；换成每卡一个进程之后线性扩展回来（4 卡 172,557，3.95×）。
