# 低精度训练

分工是固定的：**低精度负责算得快（GEMM 输入），高精度负责记得准
（主权重、优化器状态、累加器）**。「FP8 训练」指的是 GEMM 的计算精度，
不是权重的存储精度 —— 周边脚手架一律高精度。

**三组**（`ModelConfig.precision` = `bf16` / `fp8` / `fp4`）共用同一套脚手架，
**唯一的区别是主干 GEMM 用哪个量化配方**：

| 项 | 精度 | 落在哪 |
|---|---|---|
| 模型参数（计算权重） | **bf16** | `ModelConfig.param_dtype` |
| 主权重 master | **fp32** | `optim.MasterWeightAdamW` 持有 |
| 激活 / 残差流 | **bf16**（RMSNorm 内部仍走 fp32） | `torch.autocast` |
| 梯度 | **bf16**，上抬到 fp32 后裁剪 | `MasterWeightAdamW.step` |
| 优化器 m/v | **fp32** | 继承自 `torch.optim.AdamW` |
| 损失 | **fp32** | `train_steps` 里显式 `.float()` |
| FP8 组的 GEMM 输入 | **MXFP8**，前向 E4M3 / 反向 E5M2 | `fp8.recipe_for("fp8")` |
| FP4 组的 GEMM 输入 | **NVFP4**，E2M1 + 两层缩放 | `fp8.recipe_for("fp4")` |

三组的**参数存储完全相同**（同样的张量、同样的 dtype、同样的字节数），
初值也逐位相同 —— 后者靠 `make_linear` 里那句无条件的 `ref = nn.Linear(...)`
对齐 RNG 流，`tests/test_fp8.py` 有一条两两比对钉住它。

MXFP8 的缩放是每 32 个连续元素共用一个 E8M0（2 的幂）因子。
反向取 E5M2 是因为梯度的动态范围比激活宽得多，E4M3 只有 4 位指数不够用；
`MXFP8BlockScaling` 默认是纯 E4M3，必须显式要 HYBRID。

NVFP4 的数据格式是 **E2M1（4 bit，2 位尾数）**，靠四件事把它撑住 ——
`NVFP4BlockScaling()` 的**默认参数**就是这套配置，**任何 `disable_*` 都不要动**：

| 机制 | 作用 | TE 里的开关 |
|---|---|---|
| 两层缩放：每 16 元素一个 **E4M3** 因子 + 整张量一个 fp32 因子 | 单层 E8M0 在 2 位尾数上完全不够 | 无（配方固有） |
| 输入与梯度过 **16×16 随机 Hadamard** | 把离群值摊到块内，否则一个大值吃掉整块动态范围 | `disable_rht`（默认关） |
| 梯度**随机舍入** | 2 位尾数下确定性舍入会系统性地偏置梯度 | `disable_stochastic_rounding`（默认关） |
| 权重按 **16×16 二维块**量化 | 权重的离群结构是二维的 | `disable_2d_quantization`（默认关） |

实测（TE 2.17.0 / GB200 sm_100）：前向 `fp4_quant_fwd_inp` 与反向
`fp4_quant_bwd_grad` 都带 `random_hadamard_transform=True`，
反向另带 `stochastic_rounding=True`，权重侧 `fp4_2d_quantization=True`。
`tests/test_fp8.py::test_fp4_recipe_keeps_rht_and_stochastic_rounding` 钉住这一组。

## 为什么主权重必须是 fp32

在本项目自己的超参上实测。权重取实测量级 0.17（`v2-bf16` 终点档的
`blocks.8.mlp.up` 平均绝对值 0.1753，此处 bf16 的 ulp = `2^-10` ≈ 9.8e-4），
恒定梯度连更 400 步：

| 学习率 | 每步更新 | fp32 master | 无 master（bf16 直更） |
|---|---|---:|---:|
| 2e-3（峰值） | 2.05 ulp | 99.9% | 112.1% |
| **2e-4（退火终点）** | **0.20 ulp** | **100.2%** | **0.1%** |

`min_lr_ratio = 0.1`，所以 2e-4 就是余弦退火的终点学习率。**在那里，没有 master
的话更新几乎被完整吞掉** —— 权重只走了应走位移的千分之一，而训练一切看着正常。
峰值学习率下反而看不出问题（甚至偏大 12%，那是舍入噪声在随机游走），
所以这个故障只在训练后半程显现，最难查。单测
`test_updates_below_bf16_ulp_survive_only_with_master` 守这条。

## 六个踩过的坑（其中一条我最初判断错了）

### 一、低精度格点会把小更新塌回原值

这条最早是在 FP8 主权重方案里踩到的（那时权重是 MXFP8，靠随机舍入救小更新），
但**教训与具体格式无关**，所以留在这里。

当时 `write_weight_` 写成 `param.quantize_(src.to(param.dtype))`，而 `param.dtype`
是 bfloat16。结果随机舍入**完全失效**，权重几乎不动，从代码上一点看不出问题。
原因：bf16 在 0.1 附近的 ulp 是 `4.9e-4`，而抖动后「该向上进位」的窗口只有约 `1e-4` 宽；
更糟的是 bf16 的格点 `0.10546875` **恰好就是相邻两个 e4m3 格点的中点** ——
整条窗口被 bf16 塌到中点上，再按 round-half-to-even 倒回原值。

这类 bug 不写「小更新能不能存活」这条测试是发现不了的：
loss 还在降（其他参数在学），只是慢得离谱。现在这条性质由上一节那个 400 步的
对照用例守着，判据是 100% 对 0.1% —— 1000 倍的分离度。

### 二、MXFP8 要求两个维度都被 32 整除（**NVFP4 也是 32，不是 16**）

这条会一路传导到 batch size 上：主干的 token 维是 `B × 196`，而 `196 mod 32 = 4`，
所以 **B 必须是 8 的倍数**。自博弈里 `prepare()` 返回的批大小随局面数变化，
所以 `CornerNet.forward` 在量化模式下会把 batch 补齐到 8 的倍数、算完再切回来。

NVFP4 的微块是 16，很容易顺手把这个约束记成 16 —— **不对，整除要求同样是 32**。
所以 `pad_to_mxfp8` 一个字没改就通用了。记错的后果不是在启动时报错，
而是在第一批「凑不满」的自博弈批上炸，那可能是开跑几十分钟之后。

### 三、显存：三组完全一样，低精度一分钱也不省

按速查表的口径（每参数字节数）：

| | 计算权重 | 梯度 | 主权重 | m + v | 合计 |
|---|---:|---:|---:|---:|---:|
| BF16 组 | 2 | 2 | 4 | 4+4 | **16** |
| FP8 组 | 2 | 2 | 4 | 4+4 | **16** |
| FP4 组 | 2 | 2 | 4 | 4+4 | **16** |

**FP4 也是 16** —— 这一点最容易被"4 bit"三个字误导：量化只发生在 GEMM 的
输入上，是个临时量，权重从头到尾是 bf16 张量。想省显存得走「量化主权重」那条路，
而那条路本项目已经走过并放弃了（见本节末尾）。

激活侧也几乎不动：实测 batch=1024 的训练步峰值显存 38,565 MiB（BF16）对
35,307 MiB（FP8），差的那点是 TE 的量化中间量，不是结构性的。
峰值由 SwiGLU 的 hidden 激活主导，那部分两组都是 bf16。

**多出来的 fp32 master 不要钱**：训练步时 101.3 ms（BF16）/ 106.2 ms（FP8），
对比改造前的 102 / 125 ms —— BF16 组没有回退，FP8 组反而快了 15%
（省掉了每步的反量化/重量化）。`MasterWeightAdamW` 继承 `torch.optim.AdamW`
而不是自己重写更新公式，就是为了拿到 foreach/fused 内核；
手写 Python 循环的版本实测会让 BF16 组慢 12%。

**所以 FP8 在本项目里既不省显存也不提吞吐**（吞吐见下一节）。
它买的是"用上了 Blackwell 的 FP8 张量核"这件事本身，以及一份可复现的数值对照。

> 早先的 FP8 主权重方案确实省显存（权重 40%、含优化器状态 47%），
> 代价是没有 fp32 master —— 那违反了低精度训练的第一条原则，已经移除。

### 四、FP8 **不能整模型编译**（按 block 编译则没问题）

原先记的是「FP8 与 `torch.compile` 不能同时用」，`TrainConfig.resolve()` 里为此
强制关掉 compile。这条**范围记宽了**，真正的限制是：**不能把
`CornerNet.trunk` 里的 `_fp8_scope()`（TE 的 `fp8_autocast` 上下文）编进图里。**

整模型编译会把那个上下文一起包进去，而 TE 的 FP8 状态是**全局**的。多卡多线程下
各驱动并发跑起编译后的图，就 **SIGSEGV** —— 崩在第一轮自博弈，此前两次自检
都还报「FP8 计算已启用」。三个因素缺一都不炸：

| 配置 | 结果 |
|---|---|
| FP8 + compile + **单卡** | OK（smoke 22 轮） |
| FP8 + **多卡**（不 compile） | OK（18 轮） |
| **BF16** + compile + 多卡 | OK（21 轮） |
| **FP8 + compile + 多卡** | **SIGSEGV**（复现两次） |

**按 block 编译**（`selfplay.compile_for_inference`）把那个上下文留在 eager，
速度几乎没差，而且稳定：

| FP8 前向 batch=1024 | 耗时 | 多卡稳定性 |
|---|---:|---|
| eager | 37.49 ms | ✓ |
| 整模型编译 | 16.05 ms | **SIGSEGV** |
| **按 block 编译** | **15.97 ms** | ✓（双卡 smoke 11 轮） |

BF16 没有这个问题，整模型编译更快（13.46 vs 15.50 ms），保持不变。

> **教训**：孤立的单卡前向基准上，compile 值 2.17× 且 `fp8_gemm_active()`
> 报 True、数值也对得上，看着就像限制已经解除了。它没有 —— 需要多卡才显形。
> 隔离基准和真实驱动之间的差距，和「探针不能挂在告警上」是同一类问题。

### 五、调用 TE 时，当前 CUDA 设备必须与张量设备一致

在 cuda:0 建好模型再在 cuda:1 建第二份，第二份的前向会报
`cublas_gemm: the function failed to launch on the GPU`。
报错点还离根因很远 —— 最初表现为注意力里 cuDNN 的 `mha_graph.execute` 失败。

**一开始把这归因成「同进程只能用一张卡」，是错的。** 真正的原因是
TE 按**当前 CUDA 设备**取 cuBLAS 句柄：张量在 cuda:1 而当前设备是 cuda:0 就会炸。
把前向包进 `torch.cuda.device(dev)` 之后，两张卡上的 FP8 模型在同一进程里并行工作完全正常。

而且这条不匹配有**两种**表现，都难查：

- 有时**静默退回非量化计算** —— 模型看着在训练，FP8 已经名存实亡
- 有时**直接 CUDA illegal memory access**，报错点还常常飘到别的算子上

这两种表现我都撞过：先是一条一直找不到源头的警告，后来 A/B 实验把 FP8 放到 cuda:2
（训练步没设当前设备）直接崩掉。

所以护栏最终放在 **`CornerNet.forward` 里**，而不是逐个调用点打补丁 ——
训练步、自博弈、评测、Web 推理、checkpoint 读写有五六条路径，
漏掉任何一条都会以上面两种形态之一炸出来。
`torch.cuda.device` 是线程局部的，多卡多线程各设各的互不干扰。
回归测试 `test_fp8_model_works_when_current_device_differs` 专门守这条。

### 六、NVFP4 的随机 Hadamard **只吃 bf16 输入**，而 RMSNorm 会给它 fp32

这条是加 FP4 组时唯一的硬阻塞，而且 BF16/FP8 两组完全碰不到：

```
RuntimeError: quantize_impl: RHT is only supported for bfloat16 input,
              got dtype enum value 4          # 4 = kFloat32
```

炸点在 `blocks.1.attn.qkv` —— 第一个不被"首尾 block 强制 bf16"规则豁免的
`te.Linear`。根因是 **`nn.RMSNorm` 在 `torch.autocast` 下按 fp32 策略执行**，
输出 fp32，而它的下游正是 SwiGLU 与 Attention 的投影。
MXFP8 吃得下 fp32 输入，NVFP4 的 RHT 吃不下。

修法是 `model.match_dtype`：进线性层前把输入折回权重的 dtype。
**不能靠 `disable_rht` 绕开** —— 随机 Hadamard 是 FP4 收敛的必需件（见开头那张表）。

实测这个折回的影响：

| 组 | 影响 |
|---|---|
| BF16 | **逐位不变**（autocast 本来就会做同一个 cast，只是做得更晚） |
| FP8 | 极小变化：wdl 最大绝对差 4.4e-3、score 5.9e-3 |

第二条是**有意接受**的：折回之后三组喂进 GEMM 的输入 dtype 完全一致，
差别只剩量化格式本身 —— 这正是对照要隔离的那个变量。
不折的话反而多出一个「量化源精度」的差异（FP8 从 fp32 量化、FP4 从 bf16 量化）。
`test_all_legs_feed_bf16_into_the_gemm` 守这条。

### 怎么知道低精度真的在算，**而且算的是这个精度**

静默降级没法靠告警发现，只能主动查。`fp8.gemm_active(model, precision, ...)`
在主干第一个 `te.Linear` 上挂钩子跑一次前向，同时验四件事：作用域是否覆盖到
这一层（`FP8GlobalStateManager.is_fp8_enabled()`）、模块自己是否决定量化、
生效的 recipe 的**谓词**是不是这个精度（`rcp.mxfp8()` / `rcp.nvfp4()`，
用 TE 的公开语义而不是 isinstance），
以及模块自己挂着的 `quantizers` 里有没有对应精度的 `Quantizer`。
启动时、建完驱动后、以及每 `fp8_check_every_iters` 轮各查一次。

**第四条是加 FP4 组之后新加的**，因为多了一种既有的三条都抓不到的失效模式：
**fp4 被静默降级成 fp8**。那种情况下作用域开着、te.Linear 在、模块也说要量化 ——
只有量化器的实际类型能分辨。`test_probe_tells_fp4_apart_from_fp8` 双向验：
fp4 的模型上问 "是 fp8 吗" 必须答 False，反之亦然。

它有三个返回值，**三者必须区分开**：`True` / `False` / `None`（这条跑本来就是 BF16，
或者 TE 换了内部 API 查不到）。`None` 时调用方**不写** `fp8_active` 字段 ——
把「查不到」记成 `false` 会被读作「FP8 掉了」，记成 `true` 更糟。

旧探针靠捕获 `You are using quantized weights without quantized compute` 这条
UserWarning，而它只在「权重是量化张量而计算没量化」时才发。改成标准配置后
权重不再是量化张量，那条警告**永远不会出现**，探针就静默退化成恒真了 ——
一个永远说 OK 的探针比没有探针更糟。`test_probe_distinguishes_enabled_from_disabled`
守的就是探针本身的分辨力（fp8 与 fp4 各一份）。

两个教训：

1. **「A 和 B 一起用会炸」不等于「A 和 B 不能一起用」。** 先找准触发条件再下结论 ——
   我因为这个误判给 FP8 加了半天的单卡护栏。
2. **一个失效模式有两种表现时，只修看得见的那种是不够的。**
   崩溃会自己暴露，静默降级不会。

第四条曾经是 FP8 唯一真正付出的性能代价，现在已经不是了。

## 实测吞吐：FP8 的收益比预期小得多

| dim | blocks | 参数 | BF16 局面/s | FP8 局面/s | 加速比 |
|---:|---:|---:|---:|---:|---:|
| 256 | 16 | 14.2M | 28,579 | 28,452 | 1.00× |
| 512 | 16 | 56.3M | 13,599 | 13,961 | 1.03× |
| 768 | 16 | 126.3M | 8,558 | 9,011 | 1.05× |
| 1024 | 12 | 169.6M | 8,011 | 8,476 | 1.06× |

预期是约 2×，实测只有 1.00–1.06×。原因：

1. **每层的量化开销**。MXFP8 每 32 个元素一个缩放因子，每层都要对激活重新扫一遍
   求块 amax 再量化。序列只有 196 个 token，GEMM 本身不够大，这笔固定开销摊不薄。
2. **模型不是纯 GEMM**。深度可分离卷积、RMSNorm、注意力、以及 17836 维的策略头输出
   都不走 FP8，它们在总时间里占比不低。
3. D=256 时更是**核函数启动受限**：单次前向约 10 ms，和批大小几乎无关。

结论：FP8 在这个规模和这种结构上**既不省显存也不是吞吐杠杆**，算得不比 BF16 快。
但它也不再净亏 —— `torch.compile` 现在两组都能用（见第四条）。
它的价值是数值上的正确性验证，不是性能。

> 上表是 eager 下测的，两组都没开 compile，所以「FP8 不比 BF16 快」这个**相对**
> 结论仍然成立；绝对数字现在都该乘上 compile 的 2 倍多。

## FP4 的代价：更慢，且是结构性的

微基准（本项目真实形状，单个 `te.Linear`）：nvfp4 的耗时几乎**恒为 285~292 us**，
不随 batch 变化 —— 纯固定开销，加大 batch 摊不掉。训练步预计比 BF16 慢
**1.5~1.7×**（FP8 已实测 1.40×）。

根因和 FP8 那节是同一个，只是更严重：**`dim=256` 太瘦**。
同一套测量放大到 K=4096 时 FP4 反过来快 **2.03×** —— 但那对应 `dim≥4096`，
与本项目差一个数量级。

量化误差方面，FP4 是 FP8 的 **3.9 倍**（相对误差 14.6% vs 3.8%）。
参照：FP8 量化改了 9.2% 的 argmax，FP4 的策略漂移要按更大的量级预期。

**所以 FP4 组的目的是测数值边界，不是提速。** 成功判据是
「相对 BF16 组损失多少 Elo」，1.5~1.7× 的墙钟代价是既定事实，不当失败。

## BF16 对照实验

`v2-bf16` / `v2-fp8` 各跑满 15 万步，两边取最强的 4 档交叉对打 6,400 局：
**FP8 领先 +27.7 Elo [+15.4, +39.7]**，P(FP8 更强) = 100%。
数据与全部限定条件见 [FP8 训练报告 §5](../reports/FP8训练报告.md#5-与-bf16-的头对头)。

结论要连着量级一起读：**27.7 分小于「同一组从峰值训到终点」的损耗
（19~22 分）**，两者是同一档。而墙钟上 FP8 明确更慢（训练步 1.40×），
显存上完全没有收益。所以这不是「FP8 更好」，是「在这个模型宽度下 FP8 不划算，
且看不出精度代价」。

> **初值对齐是这次能做单变量对照的前提。** `te.Linear` 默认用
> `normal(0, 0.023)` 初始化而 `nn.Linear` 用 kaiming_uniform，**分布本身就不一样**；
> 两者消耗的 RNG 流长度也不同，连不含 TE 的卷积和位置嵌入都跟着错位 ——
> 不处理的话同一个 seed 下 126 个参数张量里有 **75 个逐位不同**。
> **锁住种子不等于锁住初值。** 现在 `make_linear` 一律先建 fp32 的 `nn.Linear`
> 参考层再 `copy_` 进 `te.Linear`，两组在同 seed 下初值逐位相同，有单测守着。

方案里写死了一条：**没有 BF16 对照，「FP8 无损」就是没有依据的说法。**

```bash
bash scripts/ab_experiment.sh start
bash scripts/ab_experiment.sh status
bash scripts/ab_experiment.sh compare 20000     # 在对齐步数处头对头
```

### 对照实验最容易被什么破坏

做这个对照时，下面几件事任意一件都足以让结论作废，而且都不会报错：

1. **两条的 `games_per_iter` 不同**。相同 step 下一方看到的新自博弈数据更少 ——
   而数据量是 AlphaZero 类训练的主导因素，这个差异会盖过精度带来的差异
2. **中途崩溃导致 replay 快照丢失**，buffer 从零重建
3. **只保留最近 K 份 checkpoint**，早期的被删掉之后，
   连「在同一步数处头对头」都做不到
4. **超参表被抄了第二份**。守护脚本原先自己拼了一整套启动参数，
   于是同一套配置存在两个地方。它只在**开发机过期后自动恢复**时生效，
   所以一旦两处不同步，实验会从某次恢复开始悄悄变成另一个实验，
   日志上完全看不出来 —— 而恢复正是最不容易被人盯着看的时刻。
   现在守护脚本转调 `ab_experiment.sh start-a/start-b`，配置只有一份。

5. **对照组的 metrics 里写着 `fp8_active: true`**。这条真发生过：
   `verify_fp8_compute()` 早期对**没开 FP8** 的跑也返回 `True`
   （本意是「没什么可查的」），于是 BF16 那条的 metrics 里留下了
   `fp8_active: true`。照原始 metrics 读，会得出「对照组也在用 FP8」的结论 ——
   而这恰恰是整个对照唯一要区分的变量。

   已改成对非 FP8 的跑返回 `None` 并**跳过该字段**：记成 `false` 会被读作
   「FP8 掉了」，记成 `true` 更糟。三态语义（`None` / `True` / `False`）现在是
   探针的契约，有单测守着。

6. **探针自己静默失效**。旧探针靠捕获 TE 的 `"quantized compute"` 警告判断，
   而那条警告只在「权重量化但计算没量化」时才发 —— 改成标准 FP8 配置之后它
   **永远返回 True**。一个恒真的探针比没有探针更危险：它让「FP8 没启用」这类
   问题看起来已经被排除了。现在的探针在 FP8 作用域内外分别返回 True/False，
   单测直接守这个分辨力。

判断对照是否成立有个简单的自检：**换一种对齐方式（按 step / 按累计对局数），
结论是否翻转。** 会翻转就说明它测的不是精度，是别的东西。

### 更根本的一点：跨实验比 loss 不可靠

策略目标是**网络自己的 MCTS 搜索结果**。网络变强 → 搜索出的目标更尖锐 →
可达到的 loss 随之改变。所以两条曲线的 loss 高低**不直接对应棋力**，
低 loss 也可能只是「更擅长预测自己的搜索」。

**结论只认头对头胜负**（`tools/compare_nets.py`），不认 loss 曲线。

### 锁死的控制变量

`scripts/ab_experiment.sh` 把上面这些坑一次性堵掉：

- 除 `--precision` 与设备外，全部配置逐字相同，种子相同，都从零开始
- **精度按实验名分派**（`precision_for()`：`*-fp4` / `*-fp8` / 其余 bf16），
  写死在脚本里不走环境变量 —— 守护自动恢复时只转交实验名与设备，
  靠 env 传的旋钮会在那一刻悄悄退回默认值（`v2-fp8` 的 `parallel_games`
  就是这么在第 12.8 万步被从 4096 改成 2048 的）
- `torch.compile` 三组都开，但**各走各最快的编法**（BF16 整模型，
  量化组按 block）。这是一个**已知的不对称**，接受它是因为影响比量化本身小
  （compile 换 eager 改 4.3% 的 argmax，FP8 量化改 9.2%），换来自博弈 2.4 倍
- 每 10000 步留一个永久里程碑 checkpoint，供后续在对齐步数处头对头
- 三组的**卡数必须一致**，否则每卡的并行局数不同，又多一个变量

### 三组、两台机器、分两轮

三组都要吃满 4 卡（每卡 1024 局 —— `engine_threads_per_gpu=8` 这个最优点
是绑在 1024 上实测的，同机塞两组会变成 2048），所以排成两轮：

```bash
# 第一轮
机器 1:  bash scripts/devbox.sh exec env A_EXP=v4-bf16 A_DEVICES=cuda:0,cuda:1,cuda:2,cuda:3 \
             bash scripts/ab_experiment.sh start-a
机器 2:  bash scripts/devbox.sh exec env B_EXP=v4-fp8  B_DEVICES=cuda:0,cuda:1,cuda:2,cuda:3 \
             bash scripts/ab_experiment.sh start-b
# 第二轮：机器 2 跑 start-c（v4-fp4），机器 1 空出来跑第一轮的评测
```

对称性没有被破坏：各组卡数、线程数、超参全都相同，只有 `--precision` 不同。
比起挤在一台机器上各占两张卡，好处是两组不再抢 CPU ——
自博弈是 CPU/GPU 流水，共用一台时 144 个核要分给两组，
它们的引擎线程会互相挤，而挤的程度取决于两边的进度，是个**不受控的变量**。

代价是多了一条硬约束：`runs/` 在共享 NFS 上，
**同一条实验绝不能在两台机器上同时跑**，否则 checkpoint 互相覆盖。
机器与实验的绑定写在 `.devhosts`（不进 git），守护脚本按表办事，不会自作主张换机器。

守护脚本那边有一条对称的守卫：分组**只看实验名**，
`*fp4*` / `*fp8*` / `*bf16*` 三个 case，**落不进任何一条就拒绝拉起**。
这里原先写的是 `*fp8*) start-b;; *) start-a`，加 FP4 组时 `v4-fp4` 会被静默
当成 BF16 组拉起 —— 而且只在「开发机过期后自动恢复」那一刻发生，日志上看不出来。
