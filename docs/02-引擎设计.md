# 引擎设计

引擎是整个项目的地基：训练、评测、Web 试玩共用同一份规则实现，杜绝两套规则不一致。

## 位棋盘：14×14 逻辑，16×16 物理

逻辑棋盘 14×14 = 196 格，但物理上按**每行 16 位**摆放，共 256 位 = 4 个 `uint64`。

取 16 而不是 14 的理由：行方向的邻接退化成「移 16 位」，列方向就是「移 1 位」，
八个方向的邻接全部变成一次移位。而且因为第 14/15 列与第 14/15 行永远不在 `VALID` 掩码里，
任何移位造成的**跨行绕回都会落在 `VALID` 之外**——只要移位后统一 `& VALID` 就自动清理干净，
不需要额外的防绕回列掩码。这个性质让邻接运算变成三行无分支代码：

```cpp
edge_dilate(b) = (b>>16 | b<<16 | b>>1  | b<<1 ) & VALID   // 四邻
diag_dilate(b) = (b>>17 | b>>15 | b<<15 | b<<17) & VALID   // 四角
```

刻意只用可移植位运算，不写 AVX/NEON intrinsic——目标平台是 aarch64，编译器会处理。

## 21 枚棋子 → 91 个朝向

朝向表在静态初始化时由 21 个基础形状生成：每个形状套 8 种变换（4 旋转 × 是否镜像），
归一化到包围盒左上角后去重。去重结果：

```
I1 I2 I3 V3 I4 L4 O4 S4 T4 F5 I5 L5 N5 P5 T5 U5 V5 W5 X5 Y5 Z5
 1  2  2  4  2  8  1  4  4  8  2  8  8  8  4  4  4  4  1  8  4   = 91
```

91 这个数在初始化时被断言检查——对不上说明基础形状写错了。生成顺序固定，
先出现的先占 id，动作编码的稳定性依赖于此，**不要改动生成顺序**。

## 动作空间 17836

```
action = orientation(0..90) * 196 + 包围盒左上角格号(0..195)
```

共 17,836 个动作，正好对应策略头的 `91 × 14 × 14` 张量。
其中包围盒放不进 14×14 的组合由 `action_in_bounds` 屏蔽，实际有效的是
`Σ_o (14-h_o+1)(14-w_o+1)`。

## 着法生成：从角点前沿枚举

朴素做法是盲扫 17,836 个 (朝向, 锚点) 组合，每次要流式读 570 KB 的掩码表——
按自博弈的调用频率算，内存带宽会先撑不住。

实际做法是反过来：先算出「角点前沿」，再让棋子的某一格落在前沿格上。

```cpp
allowed = ~occupied & ~edge_dilate(own) & VALID   // 可落格
anchors = diag_dilate(own) & allowed              // 角点前沿
```

遍历 `anchors` 里的每个前沿格 f，对每个剩余棋子的每个朝向的每个格 k，
令第 k 格落在 f 上，反推锚点。这样：

- **「必须角相邻」由构造保证**，不用再检查
- 只需验证所有格都落在 `allowed` 内（同时覆盖了「格为空」和「不与己方边相邻」两条规则），
  逐格早退，绝大多数候选在头一两格就被否掉
- 掩码直接从 5 个格偏移现算，不查大表，全程 cache 常驻

一个摆放可能从多个前沿格被枚举到，用 epoch 时间戳表去重（`thread_local`，
不放进 `Board` 是为了让 `Board` 保持可平凡拷贝——MCTS 里按值拷贝局面很频繁）。

首手是特例：`anchors` 只有己方起始格一个，于是「摆放必须盖住起始格」也由同一套构造保证。

## 停手与终局

`play()` 落子后自动处理：对方有着法就换手；对方无着法但己方有，则己方连走（对方停手）；
双方都无着法则终局。所以 `legal_moves()` 在非终局时永远非空。

胜负：**占格数多者胜，相同为和局**。没有「全部落完 +15」「最后一枚单格 +20」之类的加分项。

## 对称群：克莱因四元群

起始格集合 `{(4,4), (9,9)}` 在下面 4 个变换下映射到自身：

| 变换 | 映射 | 对起始格的作用 |
|---|---|---|
| ID | `(r,c) → (r,c)` | 都不动 |
| TRANSPOSE | `(r,c) → (c,r)` | 各自不动 |
| ROT180 | `(r,c) → (13-r,13-c)` | 两者互换 |
| ANTIDIAG | `(r,c) → (13-c,13-r)` | 两者互换 |

这 4 个构成克莱因四元群（每个元素自逆，任两个非单位元之积是第三个）。
90° 旋转不在其中——它把起始格映到 `(4,9)/(9,4)`，不是起始格。

### 为什么互换起始格也是合法增广

特征是**以行棋方视角编码**的，并且用两个独立平面显式区分「己方起始格」和「对方起始格」。
ROT180 之后，己方起始格落到 `(9,9)`——这只是「从另一个座位看同一盘棋」，
是完全合法、可达的局面。规则本身全是几何的，所以策略与价值在变换下等变/不变。

### 一个必须避开的坑：特征里不能放 ply

最初特征标量里放了 `ply / 42`。这会破坏 ROT180 / ANTIDIAG 的自洽性：

- 开局无停手时，先手在偶数手行棋，后手在奇数手
- ROT180 把「己方起始格在 (4,4)」变成「己方起始格在 (9,9)」，即换到了后手的座位
- 但 ply 是照抄的，于是产生「己方起始格在 (9,9) 却是偶数手」的样本——真实对局里不会出现

改成**己方占格数 / 对方占格数**两个标量：座位无关，在四个变换下都严格自洽，
且 `own + opp` 已经隐含了对局进度，信息量不比 ply 少。

## 验证

两条独立的正确性防线：

1. **规则单测**（122 项）：朝向表的连通性/归一化/去重、动作编解码往返、
   首手必须盖起始格、边相邻与角相邻规则的逐格验证、停手语义、终局判定、
   计分与胜负（含专门的和局用例）、特征平面内容、对称群性质。

2. **交叉比对**：`reference.cpp` 是一份**完全独立**的朴素实现——把局面摊成 14×14 字符网格，
   盲扫全部 17,836 个组合，逐格检查规则，不碰位棋盘、不用前沿枚举。
   两条代码路径除朝向表外无共享逻辑。

   实测 **1,000,020 个局面，零不一致**（192.6s）。

```bash
CORNERSTONE_XCHECK=1000000 python3 -m pytest tests/test_reference.py -q
```

## 性能

`random_playouts()` 全程在 C++ 里跑并释放 GIL，测出来是真实多核吞吐：

| 线程 | 对局/s | 着法生成/s |
|---:|---:|---:|
| 1 | 3,165 | 85,810 |
| 128 | 380,458 | 10,319,128 |

加速比 120×（约 94% 并行效率）。这个数字的意义是：**着法生成不会成为瓶颈**，
自博弈的瓶颈会落在 GPU 推理侧——这是正确的位置。
