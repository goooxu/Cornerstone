# Web 试玩工具

```bash
bash scripts/devbox.sh exec bash scripts/web.sh start        # 自动挑最新的 checkpoint
bash scripts/devbox.sh exec bash scripts/web.sh start <ckpt> # 指定 checkpoint
bash scripts/devbox.sh exec bash scripts/web.sh status|stop|restart
```

常驻服务，绑 `0.0.0.0:8080`，内网直接访问，无鉴权。
没有 checkpoint 时 AI 自动退回规则基线，所以训练还没出结果也能先玩。

## 一条硬规则：合法性判断不在前端重写

后端把 `legal_actions` 一次性发给前端，前端只做「这个动作在不在集合里」的查表。
落子合法性、停手、终局、计分全部走 C++ 引擎——和训练、评测用的是同一份实现。

在 JS 里重写一遍规则是最容易埋雷的做法：两边的判定迟早会分叉，
而且分叉之后表现为「网页上能下的棋，模型认为非法」这种极难定位的现象。

## 后端

`web/server.py`，FastAPI + uvicorn。

| 接口 | 作用 |
|---|---|
| `GET /api/meta` | 棋子与全部朝向的格坐标、起始格、可选模拟数 |
| `GET /api/backends` | 当前可选的对手（每次调用重新扫盘；前端在加载时取一次） |
| `POST /api/backend` | 中途换座位上的引擎 / 改模拟数，棋盘不动 |
| `POST /api/new` | 开新局，两个座位各指定一个后端（`null` = 人） |
| `POST /api/move` | 人类落子（非法着法返回 400） |
| `POST /api/ai` | AI 走一步，附带它这一步的胜率与 top 着法 |
| `POST /api/undo` | 悔棋 |

单局面搜索复用自博弈引擎：`SelfPlayEngine(num_games=1)` + `set_position(history)`
+ 跑完模拟 + `root_info()`，不调 `advance()`。没有为试玩工具单写一套搜索。

## 两个座位

先手和后手各选一个后端，其中「我来下」表示人。于是**「人机」和「AI 对战」
不是两种模式，只是同一套东西的两种填法**：

| 先手 | 后手 | 得到 |
|---|---|---|
| 我来下 | `greedy-mobility` | 人机对局 |
| `net:ab-fp8/latest` | `rule:corner-min` | AI 对战 |
| `net:ab-fp8/latest` | `net:ab-bf16/latest` | 两个模型对战 |
| 我来下 | 我来下 | 同屏两人 |

少一个「模式」开关，就少一整类「模式与实际配置对不上」的状态。
代价是 `Session.human_player` 变成了推导值，并且**两个座位都是 AI 时要返回 -1**——
返回 0 的话前端会认为先手是人，点棋盘就能替 AI 落子，`result` 方向也会错。

`▶ 自动对战` 按前端循环逐步走，不是让后端一次跑完：每步都刷新棋盘、随时能停。
800 次模拟一手要十几秒，整局跑完好几分钟，一次性返回的话页面只能干等。

### 悔棋在 AI 对战下要单独处理

人机模式的悔棋是「退到轮到人类为止」。AI 对战没有人类座位，
照这个条件找下去会一路 pop 到空棋盘 —— 表现是「悔一手把整局撤了」。
所以没有人类时就退一手。有单测守着这条。

## 选对手

界面上随时可切，两类后端：

| 后端 ID | 含义 |
|---|---|
| `rule:greedy-area` | 只看棋子格数 |
| `rule:corner-min` | 只堵对方落点 |
| `rule:greedy-mobility` | 调好权重的综合版（强度见 [03](03-基线与评测.md)） |
| `net:<跑名>/step00012345.pt` | 某个具体 checkpoint |
| `net:<跑名>/latest` | **跟随训练**，用的时候才解析 |

给这三个规则基线是因为它们各代表一种打法，正好能直观感受
「压制对方比扩张自己值钱」这条结论 —— `corner-min` 明显比 `greedy-area` 难缠。

### `latest` 必须每次重新解析

「跟随训练」的意思是选中之后还能继续跟。缓存解析结果的话，
选中那一刻就被钉死了，界面上却仍然写着「最新」—— 边训边打时
这是**看不出来的错**：你以为在跟当前权重下棋，其实是几小时前的。
所以 `resolve_backend()` 每次调用都重新读 `ckpt/latest`。

### checkpoint 会在你眼皮底下消失

训练侧的 `_prune_checkpoints()` 会轮换删除旧 checkpoint，而 `latest` 文件是
单独写的，两者之间有窗口。于是有两种正常但会炸的情况：

1. `latest` 指向的那份已经被删 → 回退到目录里实际存在的最大步数那份
2. 界面上列出来的某个具体 checkpoint，点下去时已经没了 → 返回 400
   并说明「可能已被轮换删除」，而不是 500

这两条都有单测（`tests/test_web.py`）。

### 模型按 LRU 缓存

每次走子都重新 `torch.load` 一个 100 MB 级的 checkpoint 显然不行；
无上限地缓存又会在来回切模型时把显存吃光。`BrainPool` 按解析后的路径缓存，
默认留 3 个（`--max-models`）。加载放在锁外做——读盘加建模要几秒，
占着锁会把所有请求一起堵住。

### 搜索引擎要加锁

`SelfPlayEngine` 是有状态的：`set_position` 之后必须 `prepare`/`feed` 到底。
FastAPI 的同步 handler 跑在线程池里，两个人同时点「让 AI 走」就会踩同一棵树。
表现是着法乱掉甚至崩溃，且**难复现**。所以 `NetBrain` 内部有一把锁。

### 一个踩过的坑：Pydantic 模型必须放模块级

`server.py` 开头有 `from __future__ import annotations`，注解全变成字符串。
FastAPI 要靠端点函数的 `__globals__` 去解析这些字符串——
把请求模型定义在 `build_app()` 内部就解析不到，参数会被当成 **query** 而不是 body，
所有 POST 直接 422。模型定义在模块级才行。

## 前端

`web/static/`，单页 + Canvas，无构建步骤。

- 14×14 棋盘，起始格画圈，双方用不同颜色
- 棋子托盘：21 枚，用掉的置灰。**棋子本身不可点** —— 点一枚棋子并不足以确定
  一个着法，还得选朝向。鼠标悬停时把该枚棋子的全部朝向**摊成一圈**围在四周，
  一次点击同时定下棋子与朝向（`R` 键下一形态、`F` 键跳到镜像组、`Esc` 取消）
- 悬停预览：棋子包围盒左上角落在悬停格，合法为绿、非法为红
- **当前朝向的全部合法锚点用小圆点标出**，不用靠猜
- 胜率条、top 着法列表（悬停高亮该着法的落点），在 AI 走完一步后填充
- 悔棋
- 人机对局里轮到 AI 就自动应手，没有开关 —— 关掉它只会让人每走一手
  都要多点一次「让 AI 走一步」
- **两个座位下拉**：规则基线与各训练跑的 checkpoint 分组列出，外加「我来下」，
  每个座位旁边跟一个模拟数下拉。中途换引擎**不重置棋盘** ——
  同一个局面换个引擎接着下，正是试玩要干的事。
  列表在页面加载时扫一次；训练产出新 checkpoint 后刷新页面即可
- **自动对战**：两个座位都是 AI 时可用，连着走到终局，随时可停；
  每手在棋盘下方报「谁走的 / 哪个引擎 / 用了多久」

## 模拟数与实测延迟

界面上直接选**模拟数**，不套「简单/普通/困难」这层名字，而且**每个座位一个**。

两条理由。一是名字挡着看不清实际预算：想问「同一个网络多搜一倍值多少棋力」，
就得直接看到 16 和 32。二是两个座位本来就可以是不同类型的后端，
共用一个难度时「它到底影响哪一边」永远说不清 —— 拆成每座位一个，
这个问题就不存在了。

可选 16/32/64/128/256/512/800，默认 64。规则基线不搜索，
所以它那一侧的模拟数下拉直接置灰。

上限 2000 不是审美问题：单局面搜索的批大小恒为 1，模拟数**线性**折算成等待时间，
放开了就能让一个请求把服务占住好几分钟。类型不对的由 Pydantic 挡在 422，
越界的由 `validate_sims` 挡在 400。

`RuleBrain.choose()` 接受 `sims` 但完全不用它，有单测钉着这条：
哪天规则基线真开始搜索了，置灰就该去掉。

| 模拟数 | 实测每手用时（GPU 空闲） |
|---:|---:|
| 16 | 0.08 s |
| 64 | 0.30 s |
| 256 | 1.13 s |
| 800 | 4.60 s |

上面是 GPU 空闲时的数字。**训练在跑的时候要乘 3 左右**：
实测同一台机器四张卡都在自博弈时，16 次是 0.31 s、800 次是 14.0 s。
规则基线不受影响，一直是 0.00 s。

延迟偏高的原因是**单局面搜索的批大小恒为 1**：每次模拟都要单独跑一次网络前向，
而单次前向约 10 ms 且与批大小几乎无关（见 [04](04-网络与自博弈训练.md) 末尾）。
自博弈靠「同时开几百局」攒批，单人试玩没有这个条件。

真要压下来，得在单棵树里做 virtual loss 并行展开若干叶子。对一个人机试玩工具来说
4.6 秒还在可接受范围，暂时不做——如果后面觉得慢，这是明确的优化点。
