# Web 试玩工具

```bash
bash scripts/devbox.sh exec bash scripts/web.sh start        # 自动挑最新的 checkpoint
bash scripts/devbox.sh exec bash scripts/web.sh start <ckpt> # 指定 checkpoint
bash scripts/devbox.sh exec bash scripts/web.sh status|stop|restart
```

常驻服务，绑 `0.0.0.0:8080`，内网直接访问，无鉴权。
没有 checkpoint 时 AI 自动退回规则基线，所以训练还没出结果也能先玩。

## 一条硬规则：合法性判断不在前端重写

后端把 `legal_actions` 一次性发给前端，前端只做「这个动作在不在集合里」的查表。
落子合法性、停手、终局、计分全部走 C++ 引擎——和训练、评测用的是同一份实现。

在 JS 里重写一遍规则是最容易埋雷的做法：两边的判定迟早会分叉，
而且分叉之后表现为「网页上能下的棋，模型认为非法」这种极难定位的现象。

## 后端

`web/server.py`，FastAPI + uvicorn。

| 接口 | 作用 |
|---|---|
| `GET /api/meta` | 棋子与全部朝向的格坐标、起始格、可选模拟数 |
| `GET /api/backends` | 当前可选的对手（每次调用重新扫盘；前端在加载时取一次） |
| `POST /api/backend` | 改双方或模拟数（**仅开局前 / 终局后**） |
| `POST /api/new` | 开新局，两个座位各指定一个后端（`null` = 人） |
| `POST /api/move` | 人类落子（非法着法返回 400） |
| `POST /api/ai` | AI 走一步，附带它这一步的胜率与 top 着法 |
| `POST /api/undo` | 悔棋 |

单局面搜索复用自博弈引擎：`SelfPlayEngine(num_games=1)` + `set_position(history)`
+ 跑完模拟 + `root_info()`，不调 `advance()`。没有为试玩工具单写一套搜索。

## 两个座位

先手和后手各选一个后端，其中「我来下」表示人。于是**「人机」和「AI 对战」
不是两种模式，只是同一套东西的两种填法**：

| 先手 | 后手 | 得到 |
|---|---|---|
| 我来下 | `greedy-mobility` | 人机对局 |
| `net:ab-fp8/latest` | `rule:corner-min` | AI 对战 |
| `net:ab-fp8/latest` | `net:ab-bf16/latest` | 两个模型对战 |
| 我来下 | 我来下 | 同屏两人 |

少一个「模式」开关，就少一整类「模式与实际配置对不上」的状态。
代价是 `Session.human_player` 变成了推导值，并且**两个座位都是 AI 时要返回 -1**——
返回 0 的话前端会认为先手是人，点棋盘就能替 AI 落子，`result` 方向也会错。

### 界面只有一个状态机

    idle     还没开始（或已结束）。配置可改，谁都不能落子
    playing  进行中。配置锁死，轮到谁谁落子，AI 由 pump() 驱动
    paused   已暂停。配置仍锁着，人和 AI 都不能落子

界面上每个可用/禁用状态都由这一个来源推出。之前是「自动应手」「自动对战」
「锁定」几个布尔各管一摊，组合起来有说不清的中间态
（自动对战开着但轮到人该怎么办？），按钮也有四个。现在只剩两个：

| 按钮 | idle | playing / paused |
|---|---|---|
| `btn-start` | 开始对局 | 结束对局 |
| `btn-pause` | 隐藏 | 暂停 / 恢复 |

AI 由 `pump()` 驱动：轮到的座位若是 AI 就替它走，一直走到轮到人、被暂停、
被结束或终局。人机与 AI 对战共用这一条路径 —— 以前是两套。

**暂停只能在两次落子之间生效**：一次搜索已经交给引擎了，中途打不断。
所以按下暂停后可能还要等当前这一步搜完（800 次模拟约十几秒）。

逐步走而不是让后端一次跑完，也是为了这个：每步都能刷新棋盘、都能停。

### 对局一开跑，配置就锁死

双方与模拟数只在**开局前或终局后**能改，中间一律拒绝。

原因不是实现方便，是**中途换引擎会让「这一局是谁对谁」没法陈述**：
棋盘上一半的手是 A 走的、一半是 B 走的，最后那个比分不属于任何一对组合。
早期版本允许中途换（当时的理由是「换个引擎接着下正是试玩要干的事」），
但那样得到的对局是没法引用的。要对比就该开新局。

拦截放在**服务端**（`ply > 0 且未终局` → 400）。界面把下拉置灰只是提示，
请求照样能直接发过来 —— 只做界面置灰等于没做。

界面上另有一处细节：模拟数下拉有**两种**置灰原因（规则基线用不上、对局进行中），
必须分开记，否则解锁时会把本该一直灰着的规则基线那一侧一起点亮。

### 朝向圈决定了侧栏的宽度

朝向圈要往格子外面撑（半径 42–64px，取决于该枚棋子有几个朝向），
窄栏里它会盖住半个面板。所以侧栏放宽到 480–680px，托盘从 7 列减到 6 列、
格距拉开，圈盖住邻居的比例才降到可以接受。

圈底下还垫了一层圆形暗底（`.ring::before`，直径由 JS 设的 `--r` 算出）。
没有它的话朝向缩略图会和下面压着的邻居棋子糊在一起，
根本分不清哪些是可点的选项 —— 这是「浮层必须和背景拉开层次」的老问题。

## 连续对战

**只是「开始对局」的一个选项**：局数选 1 / 100 / 200 / 400，一局下完自动开下一局，
棋盘照常逐手显示，战绩在前端累加。服务端不知道有这回事 —— 每局就是一次 `/api/new`。

要求双方都不是人（一局完要立刻开下一局，中间不能停下来等人）。
**条件不满足时整行隐藏**，而不是摆一个灰着的控件再配一句「为什么不能用」——
后者只是把界面弄复杂，并没有多给出信息。同理，单局时不显示战绩卡。

统计按局去重：`applyState` 会被调用很多次，靠 `sid` 认「这一局记过没有」。

### 曾经做成后台批量，是理解错了

第一版把它做成了「后台跑 N 局、只出统计」，复用 `evaluate_vs_network` 那条
批量路径。快是真快（100 局网络对网络约 400 秒，逐局跑要几小时），
但那不是「连续对战」——**棋盘上什么都看不到**，而且带来两条限制：
不支持纯策略、网络对网络两方模拟数必须相同（批量路径两方共用一份 MctsConfig）。

改成逐局跑之后这两条限制都没了：每步走的是单局面那条路，
两个座位各用各的模拟数、各自可以是纯策略。代价是慢，见下。

### 别对时间有错觉

逐手显示意味着每一步都是一次 HTTP 往返加一次搜索。100 局 × 约 30 手 × 2 方：

| 每步预算 | 单步耗时（GPU 空闲 / 训练中） | 100 局大概 |
|---|---|---|
| 纯策略 | 0.1 s / 2–3 s | 10 分钟 / 数小时 |
| 64 | 0.3 s / 2–3 s | 30 分钟 / 数小时 |
| 800 | 4.6 s / 14 s | 不现实 |

要跑几百局的统计，用 `tools/compare_nets.py` 或 `tools/run_arena.py`：
它们走批量路径，同样 100 局只要几分钟。界面这条是给「看着它们下」用的。

### 颜色绑对战双方，不绑先后手

逐局换边之后，「先手」不再指代任何一方 —— 同一个引擎这局执先、下局执后。
所以：

- **界面上除了选择对战双方那两行，不再出现「先手/后手」字样**，
  一律用颜色小圆点表示是谁。
- `COLORS[0]` 恒为「甲」（第一个下拉里的引擎），`COLORS[1]` 恒为「乙」，
  **和座位无关**。棋盘落子、起始格、悬停预览、棋子面板、比分格、
  状态行、战绩表全部走 `seatColor(seat)`，它内部按 `engineOfSeat()` 换算。

按座位上色的话，同一个引擎会一局一个颜色，连打时根本看不出谁是谁 ——
这正是「颜色应该和对战双方绑定」的原因。

比分格子里的名字也跟着这一局的实际座位走，完整描述放 `title`。

### 逐局交换先后手

不换边的话，得分率量的是「甲执先 vs 乙执后」，而本项目先手优势极大
（网络自博弈的先手胜率能到 0.97），那个数字和相对棋力基本无关。
换边之后甲一半局执先、一半局执后，先手优势对双方各记一半，就抵消了。

由此推出一条：**战绩必须按引擎记，不能按座位记** —— 座位每局都在换。
换边时 `players` 和 `sims` 要一起换，引擎带着自己的模拟数走。
表里另外分开报「执先胜 / 执后胜」，这两个数才看得出先手优势有多大。

战绩卡放在**棋盘下方**：连打时眼睛在棋盘上，统计跟着一起看才顺。

### 模型标签要写全：精度 + step + 模拟数

    CornerNet 14.2M · FP8 · step 135852 · 64 次模拟

三样缺一不可：

- **精度**：`ab-fp8` 和 `ab-bf16` 的 checkpoint 混在同一个下拉里，
  光看 step 分不出是哪一条。这个标志取自 checkpoint 自带的 `model_config`，
  **不是从跑名猜的** —— 跑名可以随便起，模型配置不会骗人。
- **step**：训练到哪儿了。
- **模拟数**：同一个 checkpoint 用 800 次模拟和用纯策略完全是两个对手，
  搜索量对棋力的影响不比 step 小。规则基线不搜索，就不写这一项。

顶部徽标、「上一手」那行、战绩表的引擎名都用这套。连续对战会换边，
所以徽标按**当前这一局的实际座位**显示，不看下拉框顺序。

### 终局提示不能盖住盘面

第一版把横幅画在画布正中间 —— 醒目是醒目，但**一局刚结束正是要看盘面的时候**，
盖上去等于把要看的东西挡了。

改成棋盘**上方**的独立 DOM 元素：大字判词 + 占格比分 + 手数，
边框和文字取胜方的颜色；同时棋盘容器的描边也跟着变色（边框不占格子）。
两处都不遮挡任何一个棋盘格。

连续对战每局之间停 `BETWEEN_GAMES_MS = 2000` 毫秒再开下一局 ——
没有这个停顿，棋盘会「啪」地跳到下一局的空盘，等于没看见。
停顿期间按暂停或结束能立刻退出（醒来后重新检查 `phase`）。

### 悔棋在 AI 对战下要单独处理

人机模式的悔棋是「退到轮到人类为止」。AI 对战没有人类座位，
照这个条件找下去会一路 pop 到空棋盘 —— 表现是「悔一手把整局撤了」。
所以没有人类时就退一手。有单测守着这条。

## 选对手

界面上随时可切，两类后端：

| 后端 ID | 含义 |
|---|---|
| `rule:greedy-area` | 只看棋子格数 |
| `rule:corner-min` | 只堵对方落点 |
| `rule:greedy-mobility` | 调好权重的综合版（强度见 [03](03-基线与评测.md)） |
| `net:<跑名>/step00012345.pt` | 某个具体 checkpoint |
| `net:<跑名>/latest` | **跟随训练**，用的时候才解析 |

给这三个规则基线是因为它们各代表一种打法，正好能直观感受
「压制对方比扩张自己值钱」这条结论 —— `corner-min` 明显比 `greedy-area` 难缠。

### `latest` 必须每次重新解析

「跟随训练」的意思是选中之后还能继续跟。缓存解析结果的话，
选中那一刻就被钉死了，界面上却仍然写着「最新」—— 边训边打时
这是**看不出来的错**：你以为在跟当前权重下棋，其实是几小时前的。
所以 `resolve_backend()` 每次调用都重新读 `ckpt/latest`。

### checkpoint 会在你眼皮底下消失

训练侧的 `_prune_checkpoints()` 会轮换删除旧 checkpoint，而 `latest` 文件是
单独写的，两者之间有窗口。于是有两种正常但会炸的情况：

1. `latest` 指向的那份已经被删 → 回退到目录里实际存在的最大步数那份
2. 界面上列出来的某个具体 checkpoint，点下去时已经没了 → 返回 400
   并说明「可能已被轮换删除」，而不是 500

这两条都有单测（`tests/test_web.py`）。

### 模型按 LRU 缓存

每次走子都重新 `torch.load` 一个 100 MB 级的 checkpoint 显然不行；
无上限地缓存又会在来回切模型时把显存吃光。`BrainPool` 按解析后的路径缓存，
默认留 3 个（`--max-models`）。加载放在锁外做——读盘加建模要几秒，
占着锁会把所有请求一起堵住。

### 搜索引擎要加锁

`SelfPlayEngine` 是有状态的：`set_position` 之后必须 `prepare`/`feed` 到底。
FastAPI 的同步 handler 跑在线程池里，两个人同时点「让 AI 走」就会踩同一棵树。
表现是着法乱掉甚至崩溃，且**难复现**。所以 `NetBrain` 内部有一把锁。

### 前端资源必须每次回源校验

页面和脚本是分开缓存的，改代码时很容易出现「新的 `index.html` 配旧的
`app.js`」。旧脚本去绑一个已经不存在的按钮，抛
`Cannot set properties of null`，**而这一抛整个模块就停了** ——
连填充下拉框的启动代码都不会执行。

表现是「选不了对战双方」，离原因隔了十万八千里：查了 HTML 嵌套、
元素 id、CSS 差异、后端字段，全都正常，因为磁盘上的代码本来就没问题。

同一个根因还有第二种表现：旧 CSS 配新 HTML 时，两个图标一起显示、
暂停按钮在对局开始前就冒出来 —— 因为隐藏它们的规则是新加的，旧样式里没有。

三道处理：

1. **资源 URL 带版本号**（`/static/app.js?v=<mtime 哈希>`）。这是主力：
   内容一变 URL 就变，浏览器手上那份根本对不上，没有「要不要复用」这个问题。
   只靠 `no-cache` 不够 —— 它只在浏览器**真的发请求**时才起作用，
   浏览器认为手上那份还新鲜的话可以连问都不问。
2. `/` 与 `/static/*` 仍带 `Cache-Control: no-cache` 兜底。
3. 绑定统一走 `on(id, event, handler)`：元素缺了就报到错误横幅上并跳过，
   **别的绑定照常** —— 一个元素对不上，不该把整个模块带停。

另外按钮的图形改成**由 JS 换 svg 内容**，不再是「两个 svg 叠着用 CSS 挑一个」。
后者一旦样式没生效就会两个一起显示；DOM 里少放一个，这种坏法就不存在了。

### 一个踩过的坑：Pydantic 模型必须放模块级

`server.py` 开头有 `from __future__ import annotations`，注解全变成字符串。
FastAPI 要靠端点函数的 `__globals__` 去解析这些字符串——
把请求模型定义在 `build_app()` 内部就解析不到，参数会被当成 **query** 而不是 body，
所有 POST 直接 422。模型定义在模块级才行。

## 前端

`web/static/`，单页 + Canvas，无构建步骤。

- 14×14 棋盘，起始格画圈，双方用不同颜色
- 棋子托盘：21 枚，用掉的置灰。**棋子本身不可点** —— 点一枚棋子并不足以确定
  一个着法，还得选朝向。鼠标悬停时把该枚棋子的全部朝向**摊成一圈**围在四周，
  一次点击同时定下棋子与朝向（`R` 键下一形态、`F` 键跳到镜像组、`Esc` 取消）。
  棋子下面不写名字 —— `I1`/`L4` 这种两三个字母对着形状看没有任何信息量。
  **两个座位都是 AI 时改成两侧各摆一块只读面板** —— 看双方还剩哪些棋子
  是 Blokus 里很实的信息（谁手里压着大件谁后面越吃紧），只是没人落子，所以不给交互
- 两个按钮：开始/结束对局、暂停/恢复。图标 + 文字，两态一起换
- 悬停预览：棋子包围盒左上角落在悬停格，合法为绿、非法为红
- **当前朝向的全部合法锚点用小圆点标出**，不用靠猜
- 胜率条、top 着法列表（悬停高亮该着法的落点），在 AI 走完一步后填充
- 悔棋
- 人机对局里轮到 AI 就自动应手，没有开关 —— 关掉它只会让人每走一手
  都要多点一次「让 AI 走一步」
- **两个座位下拉**：规则基线与各训练跑的 checkpoint 分组列出，外加「我来下」，
  每个座位旁边跟一个模拟数下拉。
  列表在页面加载时扫一次；训练产出新 checkpoint 后刷新页面即可
- **自动对战**：两个座位都是 AI 时可用，连着走到终局，随时可停；
  每手在棋盘下方报「谁走的 / 哪个引擎 / 用了多久」

## 模拟数与实测延迟

界面上直接选**模拟数**，不套「简单/普通/困难」这层名字，而且**每个座位一个**。

两条理由。一是名字挡着看不清实际预算：想问「同一个网络多搜一倍值多少棋力」，
就得直接看到 16 和 32。二是两个座位本来就可以是不同类型的后端，
共用一个难度时「它到底影响哪一边」永远说不清 —— 拆成每座位一个，
这个问题就不存在了。

可选 **纯策略 / 64 / 256 / 800**，默认 64。

### 模拟数越小反而越随机：1 次模拟不是「纯策略」

这条很反直觉，实测出来的：**`sims=1` 每局都不一样，`sims=64` 完全确定**。

原因在改进策略的这一项：

    out[i] = log(prior[i]) + sigma * q_i,   sigma = (c_visit + max_n) * c_scale

`c_visit = 50`。**一个子节点都没访问过时**，所有 `q_i` 都等于 `v_mix`，
`sigma * v_mix` 是个对所有 i 相同的常数 —— 排序完全由先验决定，确定。
**恰好访问过一个时**，`max_n = 1` 于是 `sigma = 51`，而那一个子节点用的是
它自己的 `q`。`51 × (q_j − v_mix)` 只要有 0.02 的差就是 1.0 的量级，
足以彻底盖过 log 先验之间的差距 —— 落子基本由这一次采样决定。

而「访问哪一个」来自 `init_root_sh` 里的 Gumbel 采样
（`log prior + gumbel(g.rng)` 取 top-m）。**`reset_tree` 不重置 `g.rng`**，
引擎又是按 `(NetBrain, sims)` 缓存复用的，所以每开一局都在同一条随机流上
继续取数 —— 局局不同。

模拟数一大（64），sequential halving 会把 m 个候选反复评估到收敛，
一次采样的噪声被平均掉，结果反而稳定。

所以**「纯策略」不能靠把模拟数调小来近似** —— 那恰恰是最不稳定的情形。
它是单独的一条路：`NetBrain._choose_by_policy()` 取 `root_info().priors`
的 argmax。`root.prior` 是网络 logits 在合法着法上的 softmax，
节点展开时写一次、之后再不改，既没有 Dirichlet 也没有 Gumbel，
所以**确定性**。分析面板这时显示策略本身，访问数清零（这条路上它没有意义）。

界面上的值是 `0`：字面意思就是「零次模拟」。引擎至少要跑 1 次才会展开
根节点、才有 prior 可读，多出来的那次子节点评估不影响 prior，只多约 20ms。

实测（固定 checkpoint，同一开局跑三遍）：

| 档位 | 三局前 10 手 | 单局 10 手耗时 |
|---|---|---:|
| 纯策略 | **完全一致** | 2.8 s |
| 64 | 完全一致 | 11.2 s |
| ~~1~~（已移除） | 互不相同 | 0.4 s |

**0 不行**：引擎的循环是 `while (sims_done < simulations)`，0 的话一次都不进，
根节点永远不会展开，`root_info().ready` 是 false，`choose()` 只能抛异常。

规则基线不搜索，所以它那一侧的模拟数下拉不但置灰，**还显示成「—」**——
置灰但仍显示 64，会被读成「这局它搜了 64 次」，而它根本不搜索。
切回网络后会恢复用户之前手选的值。

上限 2000 不是审美问题：单局面搜索的批大小恒为 1，模拟数**线性**折算成等待时间，
放开了就能让一个请求把服务占住好几分钟。类型不对的由 Pydantic 挡在 422，
越界的由 `validate_sims` 挡在 400。

`RuleBrain.choose()` 接受 `sims` 但完全不用它，有单测钉着这条：
哪天规则基线真开始搜索了，置灰就该去掉。

| 模拟数 | 实测每手用时（GPU 空闲） |
|---:|---:|
| 16 | 0.08 s |
| 64 | 0.30 s |
| 256 | 1.13 s |
| 800 | 4.60 s |

上面是 GPU 空闲时的数字。**训练在跑的时候要乘 3 左右**：
实测同一台机器四张卡都在自博弈时，16 次是 0.31 s、800 次是 14.0 s。
规则基线不受影响，一直是 0.00 s。

延迟偏高的原因是**单局面搜索的批大小恒为 1**：每次模拟都要单独跑一次网络前向，
而单次前向约 10 ms 且与批大小几乎无关（见 [04](04-网络与自博弈训练.md) 末尾）。
自博弈靠「同时开几百局」攒批，单人试玩没有这个条件。

真要压下来，得在单棵树里做 virtual loss 并行展开若干叶子。对一个人机试玩工具来说
4.6 秒还在可接受范围，暂时不做——如果后面觉得慢，这是明确的优化点。
