# 已知问题与后续

## 已知限制

### FP8 用不了 `torch.compile`

开着 compile 跑 FP8，先冒 TE 自定义算子的 graph break 告警，
接着编译出来的图直接 CUDA 非法访存。`TrainConfig.resolve()` 会自动关掉 compile 并打印提示。

代价是 1.8×。**不是 FP8 算得慢，是它挡住了这条加速路。** 详见 [06](06-FP8主权重.md)。

> 曾经以为还有第二条限制「同进程 FP8 只能用一张卡」。**那是误判** ——
> 真正的条件是「调用 TE 时当前 CUDA 设备要与张量设备一致」。
> 护栏现在放在 `CornerNet.forward` 里，FP8 多卡工作正常。

### 一条没查到源头的告警（未结）

FP8 训练启动时，TE 会发**一次** `You are using quantized weights without
quantized compute`。它出现在两次自检之后、第一轮自博弈期间。

已经排除的可能：主线程前向正常、工作线程前向正常、启动自检正常、
建完驱动后自检正常、`load_state_dict_into` 之后正常、跨设备调用已加护栏。
按完整启动序列复现（`Trainer` → `verify` → `make_driver`）也复现不出来。

**处理方式是把结论变成可反复测量的量而不是去追一次性告警**：
`verify_fp8_compute()` 在启动、建完驱动后、以及每个评测周期各跑一次，
把「FP8 计算是否启用」写进日志与 metrics（`fp8_active`）。
目前所有检查点都是「已启用」。

如果哪天日志里出现「未启用」，那就是这条告警对应的真实降级，届时有明确的复现入口。

### Web 试玩的高难度档偏慢

单局面搜索的批大小恒为 1，每次模拟都要单独跑一次前向。
「极难」档 800 次模拟约 4.6 秒。要压下来得在单棵树里用 virtual loss
并行展开若干叶子。见 [05](05-web试玩工具.md)。

### 自博弈与训练是严格轮流的

现在一轮里先跑自博弈再训练，两个阶段不重叠。好处是简单、可复现、
权重版本没有歧义；代价是任一阶段跑的时候另一类资源在闲着。

## 后续优先级

1. **CUDA Graph**。批的形状已经固定（`fixed_batch`），这是顺理成章的下一步，
   能再削掉一截内核下发开销。
2. **异步自博弈**。把自博弈与训练拆成独立进程，用共享内存传对局。
   顺带解决 FP8 的多卡问题（每卡一个进程，各自持有独立的 TE 状态）。
3. **加宽模型**。当前 14.2M 参数在 Blackwell 上偏瘦。等 Elo 曲线走平之后，
   `dim=384/512` 是自然的下一档 —— 也是 FP8 唯一可能真正回本的方向。
4. **单局面搜索批量化**（virtual loss），直接改善试玩体验。
5. **开局多样性**。目前靠 Gumbel 噪声与 `temperature_plies`。
   如果发现自博弈棋局趋同，可以加开局随机化或对局去重。

## 值得记住的几条经验

- **每一次「看起来是 X 慢」都要先量**。自博弈最初以为 GPU 不够快
  （GPU 占墙钟 81%），实际是核函数启动受限；修完之后瓶颈立刻跳到单线程的 C++ 侧。
  三次瓶颈转移，没有一次是靠猜对的。
- **数值 bug 不会崩，只会让效果变差**。量化前多过一道 bf16 让随机舍入完全失效，
  但 loss 照样在降。这类问题只能靠「小更新能不能存活」这种针对性测试抓出来。
- **多线程正确性要逐位对齐单线程**。竞态在这里表现为「训练效果变差」而不是崩溃。
- **报错点常常离根因很远**。FP8 多卡的根因是设备绑定，
  但最先炸的是注意力里 cuDNN 的 `mha_graph.execute`。
- **数据格式的选择要看真实分布**。策略目标存 top-32 看着够用，
  实测 `rest_prob ≈ 0.90` —— 归一化就等于把训练目标改成了另一回事。
