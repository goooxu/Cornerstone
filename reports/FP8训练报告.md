# Cornerstone：Blokus Duo 自博弈模型（FP8 混合精度）训练报告

模型结构（CornerNet）与训练方法（Gumbel-AZ 自博弈、稀疏策略目标、克莱因四元群增广、
每卡一进程 + DDP 的执行架构）与 BF16 那条**完全相同**，本报告不再重复，见
[BF16 训练报告 §2–§3](BF16训练报告.md#2-模型结构cornernet) 与 `docs/04`。
这里只写 FP8 特有的部分、训练过程、棋力，以及**与 BF16 的头对头**。

---

## 摘要

| | |
|---|---|
| 变量 | **GEMM 输入量化成 MXFP8**（前向 E4M3 / 反向 E5M2）；其余一切与 BF16 那条对齐 |
| 覆盖面 | 前向 FLOPs 的 **83.2%** 走 FP8 GEMM（34 个参数张量 / 11.8M 参数） |
| 规模 | **150,234 步 / 376 轮 / 794,241 局自博弈 / 1.54 亿个训练局面** |
| 墙钟 | **5.93 小时**（4×GB200），比 BF16 那条多 34% |
| 棋力 | **纯策略**下最强 **1609.8 Elo**（步 110,234，锚定 `random = 0`） |
| **A/B 结论** | **FP8 更强，+27.7 Elo [+15.4, +39.7]**（6,400 局跨组对局，见 [§5](#5-与-bf16-的头对头)） |

> **口径**：棋力一律是**纯策略**（每手一次前向，落 `argmax(prior)`，不做搜索）。
> 本报告的 Elo 与 BF16 报告的**不在同一次拟合里**，跨报告只看次序；
> 两组的强弱以 §5 的头对头为准。

四条主要结论：

1. **FP8 赢了这次 A/B，但赢的幅度小于「训练久了会退步」造成的损耗。**
   两边各取最强的 4 档交叉对打 6,400 局，FP8 侧得分率 **0.5398**，
   16 对里赢下 14 对，换算 **+27.7 Elo [+15.4, +39.7]**，
   4000 次自举里 P(FP8 更强) = 100%。作为尺度参照：同一组从峰值训到终点
   就要损失 18~22 分。
2. **FP8 既不省显存也不提吞吐。** 存储与 BF16 逐项相同（16 字节/参数，
   checkpoint 都是 162.5 MiB）—— MXFP8 只发生在 GEMM 里，不是存储格式。
   而在同配置区间实测，FP8 的训练步慢 **1.40×**、自博弈慢 **1.13×**。
3. **两组在**纯策略口径下**都在训练量的 73~80% 处见顶** —— FP8 终点比峰值低
   22.2 ± 9.6，BF16 低 18.9 ± 9.5。**但这个「回退」是量尺造成的**：
   把 BF16 那条的顶尖 8 档改成带 64 模拟重打，终点档反而最强
   （见 [BF16 报告 §6.4](BF16训练报告.md)）。FP8 这条没有做同样的复测，
   所以本报告里凡是「见顶/回退」的说法都只在纯策略口径下成立。
4. **FP8 的自博弈分布塌缩得更慢，但没换来「训练更久仍在涨」。**
   FP8 的先手胜率在 0.77~0.94 之间非单调地爬（终点 0.939），
   而 BF16 是 0.562 → 0.965 的单调塌缩。两条照样在同一位置见顶 ——
   「分布塌缩导致平台期」这个解释因此**不成立**。

## 1. FP8 是怎么用的

### 1.1 配置

**标准混合精度做法，不是「FP8 主权重」**：参数以 bf16 存储，
`transformer_engine` 的 `te.Linear` 在每次前向里把 GEMM 的两个输入量化成 MXFP8，
优化器持有 fp32 主权重。逐项精度与 BF16 那条**完全一致**
（见 [BF16 报告 §2.5](BF16训练报告.md#25-参数量与精度)），
**唯一的区别是 GEMM 的输入被量化**。

| | |
|---|---|
| recipe | `MXFP8BlockScaling(fp8_format=Format.HYBRID)` |
| 数据格式 | 前向 **E4M3**、反向 **E5M2**（反向的动态范围需求更大） |
| 缩放 | 块缩放，32 个元素共享一个 **E8M0** 指数 |
| 主权重 / 动量 | fp32 / fp32（与 BF16 组相同） |
| 硬约束 | GEMM 两维都必须能被 32 整除 |

### 1.2 哪些层走 FP8

```
block  0: SwiGLU             -> BF16    （首尾 block 强制高精度）
block  1..14                 -> MXFP8
block 15: SwiGLU+Attention   -> BF16    （首尾 block 强制高精度）
始终高精度：stem 卷积、位置嵌入、标量 MLP、各深度可分离卷积、全部 RMSNorm、
            注意力的 softmax 与 QK^T/AV、策略头、价值头、辅助头
```

| | BF16 配置 | FP8 配置 |
|---|---:|---:|
| 参数张量总数 | 126 | 126 |
| 其中 GEMM 走 FP8 | 0 | **34** |
| 参数量（走 FP8） | 0 | **11,796,480** |
| 每局面前向 FLOPs 合计 | 5.56G | 5.56G |
| 其中走 FP8 GEMM | 0.0% | **83.2%** |
| 计算权重 + 主权重 + m/v | 16 字节/参数 | 16 字节/参数 |

**首尾 block 强制高精度**是常规做法：第一层直接吃输入分布、最后一层直接决定
logits，量化误差在这两处的下游放大最厉害。代价是 FP8 覆盖率从 ~94% 降到 83.2%。

### 1.3 FP8 真的启用了吗

这个必须单独验证，因为 TE 在多种情况下会**静默降级**成 bf16 GEMM ——
不报错、不告警，只是没在做 FP8。探针在主干第一个 `te.Linear` 上挂钩子，
一次前向里同时查三件事：FP8 作用域有没有覆盖到这一层、模块自己的 `fp8` 标志、
recipe 是不是 `MXFP8BlockScaling`。

本次运行的 **41 次自检全部为「FP8 计算已启用」**（启动、建驱动后，以及此后每 10 轮
一次，覆盖到第 370 轮）。

> 探针本身也踩过坑：早先那版靠捕获 TE 的 `"quantized compute"` 警告来判断，
> 而那条警告只在「权重量化但计算没量化」时才发 —— 改成标准配置后它永远返回 True，
> 是一个静默失效的假探针。**空断言比没有断言更危险。**
> 现在探针在 FP8 作用域内外分别返回 True/False，有单测守着这个分辨力。

### 1.4 三个仍然成立的工程约束

1. **GEMM 两维必须能被 32 整除。** 自博弈的批必须补齐（`pad_to_mxfp8`），
   这也是驱动循环用固定批而不是按实际叶子数切片的原因之一。
2. **TE 按「当前 CUDA 设备」取 cuBLAS 句柄。** 张量在 `cuda:1` 而当前设备是
   `cuda:0` 时会报 `cublas_gemm: the function failed to launch on the GPU`，
   而且报错点常常飘到注意力的 cuDNN kernel 上，离根因很远。所有推理路径都包了
   `torch.cuda.device(...)`。
3. **FP8 不能整模型 `torch.compile`，只能按 block 编。** 整模型编译会把
   `fp8_autocast` 上下文一起包进图里，而 TE 的 FP8 状态是**全局**的；
   多卡并发跑编译后的图会 **SIGSEGV**。三个因素缺一都不炸（单卡不炸、不编译不炸、
   BF16 不炸），所以孤立的单卡基准完全测不到。按 block 编译把那个上下文留在 eager，
   速度几乎没差（batch=1024 前向：按 block 15.97 ms，整模型 16.05 ms，eager 37.49 ms）。

## 2. 训练过程

### 2.1 规模与吞吐

| | FP8 | BF16 |
|---|---:|---:|
| 步数 / 轮次 | 150,234 / 376 | 150,227 / 376 |
| 自博弈对局 | 794,241 | 796,729 |
| 墙钟 | **5.93 h** | 4.42 h |

吞吐取**两组配置完全相同的区间**（步 2,000–128,000，各 315 轮）比较 ——
FP8 那条在第 128,234 步之后换过一次并行局数，见 §2.4：

| | FP8 | BF16 | 比值 |
|---|---:|---:|---:|
| 训练 | 16.18 步/s | 22.58 步/s | **1.40×** |
| 自博弈 | 85.9 局/s | 97.3 局/s | 1.13× |
| 网络评估 | 155,324 /s | 176,639 /s | 1.14× |
| 自博弈批均 | 920 | 921 | — |

**FP8 慢在训练步上（1.40×），自博弈只慢 1.13×。** 方向和「FP8 应该更快」相反，
原因是这个模型太瘦：`D=256` 的 GEMM 在 GB200 上远没到 tensor core 的饱和区，
而 MXFP8 每次前向都要**现算块缩放并量化两个输入**，这份固定开销在小 GEMM 上
盖过了矩阵乘本身省下的时间。自博弈慢得少，是因为它的批更大（920 vs 训练的 256/卡），
量化开销摊得更薄。

![FP8 一轮的时间线](图表/FP8一轮的时间线.png)

墙钟去向：自博弈 2.8h（48%）、训练 2.6h（44%）、其它 0.5h（9%）。
一轮 52s（自博弈 25s + 训练 25s + 同步/落盘 3s），BF16 那条是 42s（22 + 18 + 2）。

### 2.2 损失曲线

![FP8 损失曲线](图表/FP8损失曲线.png)

总损失在**第 138,234 步**触底（1.4211），之后回升 3.2% 到 1.4670。
绝对值全程高于 BF16 那条：

| | FP8 | BF16 |
|---|---:|---:|
| 最低 loss | 1.4211 @ 138k | 1.2770 @ 150k（末轮） |
| 最终 loss | 1.4670 | 1.2805 |
| 最终 policy | 1.2593 | 1.1432 |
| 最终 value loss | **0.2057** | 0.1356 |
| 最终 wdl_acc | **0.9415** | 0.9659 |

**value 那两行不是「FP8 学得差」。** BF16 的 0.136 / 0.966 有相当一部分是
「猜先手赢」这个近乎常数的答案拿到的分数（先手胜率 0.965）；
FP8 的价值头面对的分布没那么极端（0.939），所以损失高、准确率低。
两个数字不能横向比 —— 它们的目标分布本来就不一样。

`policy` 与 `policy_entropy_model` 的差值中位数 5.7e-4，终点 −6.4e-4。

> **不要把它读成「策略损失 ≈ 目标本身的熵」** —— 本报告原先就是这么写的，错了。
> `policy_entropy_model`（原名 `policy_entropy`）收的是**网络自己输出**的 logits，
> 量的是 H(模型)。于是这个差是 `CE(t,m) − H(m)`，一条**温度标定条件**，
> 与拟合好坏无关；「终点 −6.4e-4」这个**负值**本身就是它不是 KL 的证据
> （真 KL 永远非负）。真实蒸馏误差 KL(t‖m) 在 BF16 组上离线测出来是 0.283 nats，
> 其中 ≥54% 是 MCTS 目标自身的采样噪声、不可约 ——
> 见 [BF16 训练报告 §7.1](BF16训练报告.md#71-loss-与棋力脱钩)。

| step | 先手胜率 | 和局率 | 平均手数 |
|---:|---:|---:|---:|
| 234 | 0.552 | 0.012 | 25.5 |
| 20,234 | 0.732 | 0.020 | 30.4 |
| 40,234 | 0.835 | 0.021 | 30.2 |
| 60,234 | 0.772 | 0.033 | 30.8 |
| 80,234 | 0.867 | 0.028 | 31.1 |
| 100,234 | 0.891 | 0.021 | 30.1 |
| 120,234 | 0.896 | 0.024 | 30.6 |
| 140,234 | 0.862 | 0.031 | 30.5 |
| 150,234 | **0.939** | **0.019** | 30.6 |

先手胜率在 0.77~0.94 之间**非单调**地爬，终点 0.939；对比 BF16 那条
0.562 → 0.965 的单调上升，FP8 的塌缩明显更慢、更不彻底。
和局率也一直保持在 2~3%（BF16 终点只剩 0.6%）。

一个未验证的猜测：MXFP8 的量化误差相当于给每次 GEMM 注入噪声，
起到了正则化 / 探索的作用，阻止了策略收窄。**这只是假设** ——
要证实需要单独做对照（例如在 BF16 组上人为注入同量级噪声）。

**但塌缩得慢并没有换来「训练更久仍在涨」** —— 见 §3.2，两组都在
训练量的 73~80% 处见顶。

### 2.4 一次中途重启（必须披露）

这组在第 **127,834** 步（第 320 轮）中断过一次，守护脚本在约 5 分钟后从
checkpoint 恢复，replay buffer 的 2,999,995 个局面完整恢复，没有数据丢失。

**但恢复时 `parallel_games` 从 4096 变成了 2048**（守护脚本转交给
`ab_experiment.sh` 时用了该组的历史默认值）。影响：

| | 前 319 轮 | 后 57 轮 |
|---|---:|---:|
| 每卡并行局数 | 1024 | 512 |
| 自博弈批均 | 920 | 461 |
| 自博弈 | 85.8 局/s | 49.0 局/s |
| 训练 | 16.18 步/s | 15.96 步/s |

- **对数据生成的语义没有影响**：`games_per_iter` 仍是 2048，每局的搜索彼此独立，
  改变的只是「同时开多少局」，也就是 GPU 批的利用率。
- **对墙钟有影响**：这 57 轮因此多花约 **0.29 小时**。若全程保持 4096，
  FP8 的墙钟约为 **5.64 小时**（相对 BF16 是 1.28× 而不是 1.34×）。
- **对 §5 的 A/B 结论基本没有影响**：两组用于头对头的顶尖档里，
  只有 `130,234` 一档落在变更之后的区间。把它整档剔除后重算，
  FP8 的领先反而从 +27.7 扩大到 **+33.7 Elo**（4,800 局）——
  也就是说这个瑕疵在稀释结论而不是制造结论。

BF16 那条全程单次连续运行，没有中断。

## 3. 棋力评测

方法与 [BF16 报告 §5](BF16训练报告.md#5-评测方法) 完全一致：15 档 checkpoint
（10,234 … 150,234）+ 5 个规则基线放进**同一场单循环**，全对全 190 对 × 400 局，
纯策略、开局随机 2 手且成对（同一开局双方各执先一次），锚定 `random = 0`，
误差按「对」自举 2000 次。

### 3.2 终点比峰值低 22 分

| 与 110,234 相比 | Δ Elo | ± | P(110,234 更强) | 直接头对头 |
|---|---:|---:|---:|---:|
| 150,234（终点） | **+22.2** | 9.5 | **99.2%** | **0.481** |
| 130,234 | +10.1 | 9.6 | 86.2% | 0.507 |
| 80,234 | +8.5 | 9.5 | 82.0% | 0.516 |
| 100,234 | +7.5 | 9.4 | 79.7% | 0.514 |
| 40,234 | +104.7 | 9.5 | 100.0% | 0.639 |
| 10,234 | +536.3 | 13.5 | 100.0% | 0.968 |

第一行是个漂亮的不可传递性例子：**110,234 对 150,234 的直接头对头是 0.481 ——
终点档赢了峰值档**，但对全部 19 个对手的总成绩仍是峰值档高 22 分。
这正是要用联合拟合而不是单条边的原因，也是「单一 Elo 数字只是近似」的现成证据。

**在纯策略口径下**，第 11 万步之后的 4 万步训练（占总量的 27%）是净损耗。
⚠️ 这句话不能外推到实际使用场景：BF16 那组做过带 64 模拟的复测，
结论整个反过来（终点档最强）。FP8 这条没有复测过，所以只能说
「先验的 argmax 质量在退」，不能说「棋力在退」。
对照 BF16：峰值在 12 万步（80%），终点低 18.9 分。两组的形状一致。

### 3.3 测量的边界

- **纯策略口径**，网络不带搜索。加上搜索会显著更强，但那是另一个口径。
- **绝对刻度靠一条弱边**：纯策略下第 1 万步的网络就远强于全部规则基线，
  网络这一块与规则阶梯之间几乎只剩 `greedy-mobility` 那条边。
  可靠的是档位之间的排序（±9.6），不是绝对值（±34）。
- **Bradley-Terry 假设可传递**，而近实力档位之间存在不可传递性（§3.2）。
- **单次运行，n=1**，且中途重启过一次（§2.4）。

## 4. 跨表不可比

`greedy-mobility` 在两场拟合里分别是 **824.6**（BF16 场）和 **863.9**（FP8 场），
差 39 分 —— 同一个确定性规则智能体、同样的对局口径，只是对手池不同。
所以本报告的 1609.8 和 BF16 报告的 1522.6 **是两把尺子上的读数，直接相减没有意义**。

两组的强弱只能靠直接头对头。

| 110227 | 0.453 | 0.445 | 0.491 | 0.479 | 0.467 |
| 130227 | 0.448 | 0.430 | 0.456 | 0.507 | 0.460 |
| **列均** | 0.446 | 0.441 | 0.468 | 0.486 | |

（表内为 **BF16 侧的得分率**，<0.5 即 FP8 赢。）

**16 对里 FP8 赢下 14 对**，输掉的两对都是对 FP8 最弱的那档（`130234`）。
合计 6,400 局，BF16 侧得分率 **0.4602**，95% 区间 [0.4431, 0.4778]，
换算 **FP8 +27.7 Elo [+15.4, +39.7]**，4000 次自举里 P(FP8 更强) = **100.0%**。

同一次拟合里的排位也一致 —— **FP8 的四档包揽 1~4 名，BF16 的四档是 5~8 名**：

| | Elo（不锚定，相对量） |
|---|---:|
| net@100234（FP8） | 45.7 |
| net@110234（FP8） | 32.5 |
| net@80234（FP8） | 30.0 |
| net@130234（FP8） | 14.6 |
| net@110227（BF16） | 11.1 |
| net@130227（BF16） | 2.0 |
| net@120227（BF16） | 0.0 |
| net@100227（BF16） | −1.0 |

### 5.1 这个结论有多干净

**锁死了的：** 除 `--fp8` 外全部超参逐字相同、种子相同、都从零开始、
卡数相同（各 4 张）、执行架构相同（每卡一进程 + DDP）、精度方案的其余各项相同
（bf16 计算权重 + fp32 主权重 + fp32 动量 + bf16 梯度）、**初始权重逐位相同**。

最后一条值得单说：`te.Linear` 的默认初始化是 `normal(0, 0.023)`，
而 `nn.Linear` 是 kaiming uniform，**分布本身就不一样**，消耗的 RNG 流也不同 ——
不处理的话同一个 seed 下 126 个参数张量里有 75 个逐位不同，连不含 TE 层的
`pos`、`spatial.conv` 也跟着错位。**锁住种子不等于锁住初值。**
现在 `make_linear` 一律先建 fp32 的 `nn.Linear` 参考层再 `copy_` 进去，
两组从此在同 seed 下初值逐位相同。

**没锁死的，两条：**

1. **`torch.compile` 的编法不同** —— BF16 整模型编，FP8 只能按 block 编
   （整模型会 SIGSEGV，见 §1.4）。两边的算子融合因此不同，严格说多了一个变量。
   接受它是因为影响比 FP8 量化本身小（compile 换 eager 改 4.3% 的 argmax，
   FP8 量化改 9.2%），而换来的是自博弈 2.4 倍。**这是有意的取舍，不是疏漏。**
2. **FP8 组最后 15% 的并行局数减半**（§2.4）。对数据语义无影响；
   剔除受影响的那一档后 FP8 领先反而更大。

**没排除的：** n=1。自举误差只覆盖对局采样噪声，**不覆盖训练本身的种子方差**。
±12 说的是「同一对权重再打 6,400 局会怎样」，不是「换个种子重训一遍会怎样」。
在两组只差 27.7 分、而同一组从峰值训到终点就要掉 18~22 分的量级上，
**这个结论应当读成「这次实验里 FP8 不弱于 BF16」，而不是「FP8 更好」。**

### 5.2 结论

**FP8 在本项目里的账是：棋力 +27.7 Elo，墙钟 +34%，显存 ±0。**

- 棋力上没有观察到 FP8 的代价，这次甚至是正的 —— 但幅度小于训练步数选择的影响。
- 墙钟上是明确的负收益。根因是模型太瘦（`D=256`）：量化的固定开销盖过了
  小 GEMM 省下的时间。**这条不能外推到更宽的模型** ——
  §7 的加宽计划落地后应当重测。
- 显存上完全没有收益：MXFP8 只发生在 GEMM 里，权重和优化器状态一字节没少。

一句话：**在当前这套超参和这个模型宽度下，FP8 不值得。**
值得的前提是模型足够宽到让 GEMM 真正成为瓶颈。

## 6. 观察与结论

### 6.1 「分布塌缩导致平台期」被证伪

BF16 那条的诊断曾经指向自博弈分布塌缩（先手胜率 → 0.965，价值头在学常数）。
FP8 提供了一个对照：**它的先手胜率非单调、终点 0.939、和局率还有 1.9%，
塌缩程度明显更轻，却同样在第 11 万步见顶，之后掉得还更多（−22 vs −19）。**

所以平台期的原因不是（或不只是）分布塌缩。两组共有而可能相关的因素还有：
每手只有 64 次模拟、`temperature_plies=12` 相对 30 手的对局偏短、
没有 Dirichlet 噪声这类显式探索项、以及**自博弈的对手永远只有当前的自己**。

### 6.2 两组都在训练量的 73~80% 处见顶

| | 峰值步数 | 占训练量 | 前 4 万步拿到的增长 | 终点相对峰值 |
|---|---:|---:|---:|---:|
| BF16 | 120,227 | 80% | 83% | −18.9 ± 9.5 |
| FP8 | 110,234 | 73% | 80% | −22.2 ± 9.6 |

**两组都是训练到 27% 时就基本到位，最后 20~27% 是净损耗。**
这个一致性比任何单组的曲线都更有说服力，也说明它不是某组的偶发现象。

### 6.3 下一步

按这次数据给出的优先级：

1. **先解决「训练越久越差」，再谈精度选型。** 两组都在 73~80% 处见顶、
   之后倒退 19~22 分。在这个问题解决之前，FP8 与 BF16 差的这 28 分意义有限 ——
   两者是同一量级。
2. **建立能持续区分强弱的量尺。** 规则阶梯在训练走完 7% 时就被打穿了
   （第 1 万步的网络已远强于 `greedy-mobility`），后 93% 的训练没有有效进度信号。
   历史 checkpoint 是现成的、会随训练一起变强的对手。
3. **加宽模型后重测 FP8 的墙钟账。** §5.2 的「FP8 更慢」绑在 `D=256` 上，
   量化开销是固定的、GEMM 收益随宽度增长，`D=512` 很可能翻转结论。
4. **「FP8 噪声起到正则化作用」这个假设值得验证** —— 在 BF16 组上人为注入
   同量级噪声，看先手胜率是否同样不塌缩。这条能把 §2.3 的猜测变成结论。
5. **换种子重跑一次。** §5.1 里唯一没排除的就是训练方差，而结论的量级
   （28 分）和它可能的方差是同一档。

## 7. 复现

```bash
# 起训（四卡，每卡一个工作进程）
bash scripts/devbox.sh exec env B_EXP=v2-fp8 B_DEVICES=cuda:0,cuda:1,cuda:2,cuda:3 \
     bash scripts/ab_experiment.sh start-b

# 棋力评测：15 档 + 5 个规则基线单循环，190 对
bash scripts/devbox.sh exec python3 tools/net_arena.py \
  --nets ../runs/v2-fp8/ckpt/step*.pt \
  --rules random greedy-area flat-mcts-256 flat-mcts-1k greedy-mobility \
  --games 400 --simulations 0 --engine-threads 8 --pairs all \
  --out ../runs/arena_v2_fp8.json

bash scripts/devbox.sh exec python3 tools/arena_best.py \
  ../runs/arena_v2_fp8.json --boot 2000 --top 8 \
  --plot reports/图表/FP8棋力曲线.png

# A/B：两边各取最强的 4 档交叉对打（§5），28 对约 72 秒
bash scripts/devbox.sh exec python3 tools/net_arena.py --anchor none \
  --nets ../runs/v2-bf16/ckpt/step00{120227,100227,110227,130227}.pt \
         ../runs/v2-fp8/ckpt/step00{110234,100234,080234,130234}.pt \
  --games 400 --simulations 0 --engine-threads 8 --pairs all \
  --out ../runs/cross_ab.json

bash scripts/devbox.sh exec python3 tools/cross_arm.py ../runs/cross_ab.json \
  --a net@120227 net@100227 net@110227 net@130227 \
  --b net@110234 net@100234 net@80234  net@130234

# FP8 是否真的启用：训练日志里每 10 轮一条自检
grep '\[自检\]' ../runs/v2-fp8/train.log | sort | uniq -c
```
